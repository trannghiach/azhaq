# Architecture

Azhaq takes seeds, runs every collector that accepts each seed's type, and stores what they report in a SQLite graph. Facts a collector reports can become new seeds, so a run expands outward until it hits its depth or item limit.

```
seeds ──► Plan ──► Run ──► observations ──► graph (SQLite)
            ▲                    │
            └──── next seeds ◄───┘
```

## Data model

**Seeds** have a type and a set of keys. Collectors exist today for `URL`, `Hostname`, `Domain`, `IPAddress` (ports, TLS, reverse DNS, network), `Prefix` and `ASN` (announced prefixes, reverse DNS of a range), `Organization` and `CloudAccount`. `Certificate`, `Email` and `Application` are defined but unused.

**Entities** are graph nodes, unique on `(type, key)`. Keys are normalized before lookup (lowercase hostnames, cleaned URLs), so the same hostname found by CT, DNS, a crawl and a certificate SAN is one entity.

**Observations** are facts attached to an entity: collector, source, kind (`url`, `dns`, `ct`, `form`, `params`, …), a JSON payload, confidence and timestamp. They are append-only. A later observation does not replace an earlier one.

**Edges** are derived from observations and seeds:

| Edge | Meaning |
| --- | --- |
| `FOUND` | a URL was found on another URL |
| `ON_HOST` | a URL belongs to a hostname or IP |
| `IN_DOMAIN` | a hostname belongs to a registrable domain (eTLD+1) |
| `RESOLVES_TO` | a hostname resolves to an IP |
| `CNAME` | a hostname is an alias of another |

Identity rules that keep the graph honest:

- Hostnames on shared platforms (`appspot.com`, `herokuapp.com`, `web.app`, …) stop at the tenant, so two tenants are two sites.
- Hosts that share an IP are not merged.
- TLS SANs are only followed within the seed's eTLD+1, which ignores CDN and proxy default certificates.

## Collectors and the catalog

A collector is one interface:

```go
type Collector interface {
	Name() string
	Inputs() []types.SeedType
	Outputs() []string
	Run(ctx context.Context, seed types.Seed, emit func(types.Observation) error) (types.RunMeta, error)
}
```

`Run` only reports: it calls `emit` for each fact and returns follow-up seeds in `RunMeta.NextHints`. It never writes the graph or schedules work.

All collectors register in one in-process catalog (`catalog`, filled by `collectors.RegisterAll`). Planning is a lookup, `catalog.Where(seed.Type)`, so the engine and CLI never name a collector. Adding a capability means writing a collector and registering it.

A collector may also implement:

- `catalog.Informer` (`Info()`), which says what it contacts. `Passive` collectors only ask third parties and DNS resolvers; `Touch` collectors (the default) send requests to the target; `Active` collectors send guesses (brute force, permutations) and name the flag that enables them. `After` names a collector that must finish with the same seed first: HTTP and TLS wait for `azhaq-dns`, and when DNS returns `RunMeta.Drop` (no address, or a wildcard answer) they skip the name.
- `catalog.Batcher` (`BatchSize`, `RunBatch`), for work that is much cheaper in bulk. DNS resolves up to 256 names per call; each name still gets its own entity, idempotency key and hints.
- `catalog.Skipper` (`Skip(seed) bool`), to decline a seed when it would return at once: a script it has already parsed, an origin whose paths it has already swept, a URL that cannot be an API description. Skipped seeds do not spend the item budget.

A collector can also hand over seeds before it returns with `catalog.Hint(ctx, seeds...)`. The subdomain collector does this as each source answers, so DNS starts on the fast sources' names while a slow source is still running.

## Engine

`engine` exposes four operations:

- **Plan** turns seeds into work items, one per matching collector.
- **Run** executes one work item. It upserts the seed entity, passes an `emit` function that writes each observation and its edges to the store, then returns the collector's hints plus derived seeds (URL → hostname → eTLD+1). Each item has an idempotency key, a hash of collector, seed type and seed key. An item already in the store is skipped, so retries are free.
- **Ingest** writes facts produced outside Azhaq (connector JSONL) straight into the graph.
- **RunLocal** is the built-in scheduler the CLI uses. A workflow engine can call `Plan` and `Run` directly and do its own scheduling instead.

`emit` writes synchronously, so a fast collector cannot outrun the store and memory stays flat.

### Scheduling (`RunLocal`)

Work flows instead of moving in waves. A seed's work items are queued as soon as the seed appears, a free worker takes the next one, and the hints it returns are queued at once. A slow item, such as a CT log taking 25 seconds, holds back nothing else. Up to `-parallel` items (default 16) run at a time; each batch collector may run 4 batches at once on top.

Limits:

- `-depth` (default 4) bounds how many hints away from the seeds a seed may be.
- `-max-items` (default 2048) caps ordinary work items.
- `-max-names` (default 20,000) caps the names handed to batch collectors (DNS), so a domain with thousands of subdomains does not spend the item budget on resolution.
- `-max-requests` caps the requests sent to targets, and `-rate` paces them over all hosts. Every request to a target asks `fetch.Spend` first: GETs and each redirect hop, path and parameter guesses, the GraphQL query, and a page loaded in Chrome. Every other request Chrome sends (a page's scripts, images and calls, a redirect, a login, a WebSocket's handshake) is counted as it leaves (`fetch.Take`), paced by `-rate` like the run's own, and refused once the budget is spent; a page or a screenshot that lost requests to the budget ends `capped`, and is loaded again by `azhaq resume`. `-daily-requests` gives a program (`-program`, else the run's targets) a number of requests per UTC day, counted over the runs in the database (table `spend`); a run starts with what is left.

A request the budget refuses fails with `neterr.ErrBudget`. The engine marks every task's context, so a refusal counts even when a collector takes the failed request for a missing page: the task ends `capped`, is not marked done, drops nothing that waits on it, and the run is marked `capped`. Under a budget a task's reports are held until it ends, and those of a task the budget stopped are dropped: a refused catch-all check would otherwise turn an application's index page into findings.

An origin (scheme, host and port) that does not answer 5 requests in a row, connects refused or without a route, or timeouts, with no answer between them, is stopped for the rest of the run: its remaining requests are refused with `neterr.ErrOriginDown` instead of each taking a timeout, the tasks that asked end `capped` and are left for `azhaq resume`, which tries the origin again, and the summary lists them under `left alone` with `ORIGIN stopped answering after 5 timeouts` and names the origin in `stopped`. Any answer starts the count over; a request the run itself cancelled does not count. Only the 5 timeouts are failures. The check of `http://host/` for a host given as https treats a stopped origin as nothing listening.

### Resuming (`azhaq resume`)

The scheduler records its frontier in the store (table `tasks`): every task it plans (collector, seed, depth), in the same transaction as the tasks that finished, so a task's hints are never lost between it ending and them being recorded. A task is done when it ran (with or without an error), was dropped, or was skipped; one that was cancelled or stopped by the request budget is not. The run's options are stored with it, without the database or the values that carry a session (`-cookie`, `-login-pass`, headers named like a credential).

`azhaq resume -db FILE` takes the latest run with tasks left (interrupted by Ctrl-C or a kill, or stopped by `-max-requests`, `-daily-requests` or `-max-items`), runs it again with its stored options plus any given, and rebuilds the queues from the tasks: done tasks count against the item budget, the others are queued again, behind the task they wait for when that is not done either. Their done-marks are cleared, so a task that ran but whose end was not recorded runs again whole; observations are stored once per run, so it reports nothing twice. Tasks the budget stopped before run last, one at a time and cheapest first (by the requests they had sent), so a path sweep that needs more than the budget does not starve cheaper work; once the budget is spent, tasks that would contact targets are kept back. A resume in which no task finished says the budget is smaller than any task left needs.

### The request ledger and the kill switch

`internal/ledger` keeps a tamper-evident record of what a run sends to a target. Each entry is one JSON line (`seq`, `time`, `kind`, `method`, `target`, `host`, `rule`, `collector`, `prev`, `hash`), and `hash` is the sha256 of `prev` and the entry's JSON without `hash`, so an edited, removed or reordered line breaks the chain from there on. A line is flushed before the request goes, so a crash loses nothing that was sent. `Open` continues the chain of a file that exists: `azhaq resume` and later runs into the workspace append to the same file, and `azhaq roles` opens one ledger in its `-dir` for all its runs. The hooks are where a request leaves the process: `fetch.Client` and `fetch.Do` wrap every target-facing transport (`kind` `http`), `portscan` and `tlscol` record connects (`tcp`) and datagrams (`udp`), and the browser records the requests it lets Chrome send (`chrome`). DNS queries and the third-party sources are not targets and are not recorded, and neither are the requests of a connector, which Azhaq does not send. `Match` names the scope rule that allows each host, from the run's `-allow` and `-scope`.

`fetch.SetKill` watches for the kill file every 100 ms (`fetch.KillCheck`); once seen, it also ends every wait for the pace (`fetch.Pace`), so a request counted before the file appeared is not sent after it. Once it exists, `Spend`, `Take` and `Spent` refuse with `neterr.ErrKilled`, which is also an `ErrBudget`: every collector that leaves work for `azhaq resume` on a spent budget does so here, and the run ends exit 4 with `stopped` naming the kill switch. Without a workspace of its own (a drop-in command without `-db`) a run has no default ledger or kill file.

### Workers (`-serve`, `azhaq worker`)

A run started with `-serve ADDR` lends its work to `azhaq worker` processes, on the same machine or others, over HTTP with a bearer token. The run's process keeps the database, the scheduler, the budgets and its own `-parallel` slots; a worker claims one task at a time per slot (`POST /v1/claim`, a long poll), runs the collector in-process without a store (`engine.Execute`) and sends back what it reported, its hints and the requests it sent (`POST /v1/done`), which the run stores as if it had run the task itself (`Engine.Record`). Workers take only tasks that contact targets: third-party sources (and their keys), batch DNS and `Local` collectors (screenshots, `-browser`) stay with the run. A worker gets the run's options without seeds, outputs or sessions, the files they name (wordlists), the scope as `-allow`/`-deny` rules and the session as headers (`GET /v1/run`). A task a worker holds longer than its lease (15 minutes) is queued again; tasks lent when the run stops are left for `azhaq resume`. The request budget counts every process's requests; `-rate` and `-host-parallel` apply per process.

Items on the seed's own host or IP run before fan-out items, but part of the item budget is reserved for fan-out: one eighth, at least 24 items once the budget is 48 or more, and never more than half. Without it, a large application would spend the entire budget before any domain-level collector ran.

The run's policy is applied when items are planned: `-passive` keeps only `Passive` collectors; an `Active` collector needs its flag and a seed inside the scope, which is the `-allow` or `-scope` given or, when there is none, the targets given; `-skip` removes collectors by name.

A seen-set prevents running the same seed twice, and `-allow` / `-deny` / `-scope` filter hints before they are queued. A scope entry is a domain with its subdomains (`example.com`, `*.example.com`), one host (`=api.example.com`), or an address range (`10.0.0.0/8`). When a scope is set, the shared HTTP client also refuses any request to a host outside it, and stops following a redirect at the first hop that leaves it (the hop is recorded with its `Location`); the path, parameter and GraphQL modules use their own clients without redirects, on seeds the scope already admitted. Chrome is held to the same scope (see [Chrome and the scope](#chrome-and-the-scope)).

Collectors that read a page (crawl, scripts, API descriptions, paths, GraphQL) run after `azhaq-http` has answered for the same URL: a URL that does not answer is dropped, and so is every task waiting behind it. A target given as `host:port` or an IP address goes on as the scheme that answered. A target given as `https://host/` that archives or links name over plain http (`http://host/…`, or another name of its domain) gets one request to `http://host/` first: when it redirects to https on the same host, serves the same front page (behind a redirect, the same page where both redirects end: two applications each send their visitors to their own `/login`), or nothing listens on port 80 (the connection refused, no route, a name without an address, or a connect that times out twice), those URLs are the https site's and are requested and mapped as https; otherwise, a slow answer or one that is not HTTP included, `http://host/` is a service of its own and its URLs stay as they are. A directory listing's sort links (Apache's and nginx's `?C=N;O=D`, `?C=M&O=A`) are the same listing and are neither requested nor listed. URLs that differ only by an ID or a query value share a template (`/catalog/product?productId={n}`); at most 3 URLs per template are fetched, and the rest stay in the graph as found. Within a host, work runs by what it is worth under a budget: the service and its front page first, then its API and description paths, then the pages links and scripts name, and what only an archive lists last, so a program run spends `-max-requests` on the front pages and APIs of its hosts before on archived URLs; a front page found late goes ahead of archived URLs queued before it. Work left over when a limit is reached is stored and the run is marked `capped`.

## HTTP

All HTTP collectors share one client (`internal/fetch`):

- Redirects are not followed automatically. Each hop is recorded, and the status stored is that of the URL that was requested, so `/admin → 303 → /login` records `/admin` as 303.
- At most 10 requests are in flight per host (`-host-parallel`, katana's concurrency). Concurrent requests for the same URL share one fetch.
- Bodies are capped at 2 MiB, or 16 MiB for JavaScript, JSON and source maps, where bundles of several MB are normal. `-delay` adds a pause before each uncached request.
- `-cookie` and `-header` are added to every request, which lets a run reuse a session you already have; `-login` gets one with Chrome. Azhaq stores cookie names but never their values.
- Headers must arrive within 10 seconds, as in httpx; CDN edges and bot managers often answer slowly. The whole request, body included, gets 30 seconds, so a large bundle on a slow link still arrives.

### Probing

`azhaq-http` probes a hostname over HTTPS and falls back to HTTP; with `-web-ports` it tries each port, HTTPS first except on port 80. A `host:port` or IP address from `-list` becomes a URL with the same fallback. For each answer it stores, besides status, title and headers:

- `tech`: wappalyzer fingerprints of the final response's headers and body, as `Name` or `Name:version`. `internal/wappalyzer` is wappalyzergo's passive matcher with one change: each pattern's regexp compiles the first time its literal prefilter passes. Upstream compiles all of them at load, and because it bounds `+` and `*` to 250 repetitions, which Go unrolls, that held about 80 MB; on first use it is a few MB. A test runs both matchers over a page built for each of the 7,642 fingerprints and requires identical results;
- `favicon`: on a site's front page, the MurmurHash3 of the icon's base64 encoding, the value Shodan indexes as `http.favicon.hash`. The icon is the page's `<link rel=icon>` (`.ico` first) or `/favicon.ico`, at most two requests, and only on the same site;
- `length`, `words`, `lines` of the final body (counted like httpx), `ms` for the whole redirect chain, and `ip`, the address the request connected to (left out behind a proxy);
- `final_status` when the request was redirected.

`azhaq-dns` adds `cdn` and `cdn_type` (`cdn`, `waf` or `cloud`) from cdncheck's embedded ranges: by address, then by CNAME target. Nothing here makes an extra lookup.

`-probe` keeps a run to this: only `azhaq-dns` and `azhaq-http` run, on the listed targets and nothing they lead to, and the output is one line per web service instead of the map.

`azhaq probe` runs `-probe` with httpx's settings (`httpcol.Spec`): no redirect followed unless `-fr` (and then `-maxr` as httpx counts it, at most N-1 hops, within the site or, with `-fhr`, the host); no `Accept` header and one connection per request, as httpx sends; TLS 1.0 and up; a bare `host:port` asked over plain HTTP first on 8080 and on ports above 1024, and over TLS when the plain request is answered 400; the scheme order, `-p` ports (also for addresses), `-path`, `-nf` and `-pa`. A name that resolves only through a wildcard answer is probed, not dropped. Every answer keeps its request and response as they went over the wire (`fetch.Result.Raw`): the matchers (`internal/probefilter`), `-hash`, `-sr`, `-irr`, `-tls-grab` (read from the handshake the request made, no extra connection) and `-debug-*` read it. The request a method, body or header changes (`-x`, `-body`, `-rr`, `-vi`, `-pa`) is a request of its own: its answer is cached and kept under a key that holds them (`fetch.DoReq`), so it never answers for the plain GET. `-jarm`, `-http2`, `-pipeline` and `-vhost` send extra requests, each counted and paced like any other. `-tls-probe` and `-csp-probe` raise the depth so the names a certificate or a policy gives are probed too, inside the scope. `-kb` classifies pages with the dit model, which is read from `~/.dit/model.json` or `$AZHAQ_DIT_MODEL` and never downloaded.

### Scripts

`azhaq-js` reads each page's inline scripts and script files, then the chunks those import by name or through a webpack chunk map: it evaluates the bundle's chunk-name function (`n.u=e=>"static/js/"+e+"."+{…}[e]+".chunk.js"`) for each chunk ID the bundle knows. A script on another host is read as Chrome would load it for the page: with a scope, when the scope allows its host; without one, when its host is on the page's registrable domain (a bundle on `cdn.example.com` for `www.example.com`; an address only itself). Those requests count against `-max-requests` and are paced by `-rate` like any other. A crawl follows links within its scope (the page's own origin; `crawl` and `-crawl-scope` widen it, see Crawling); what a script calls on another host it may request (`https://api.example.com/v1/orders`) is a row of that host, found in that script, and so is an API path it names there; a page of another host a script merely names is left to that host. A path a script on another host names (`"/api/me"`) is the page's, where the request goes. A path a script joins to a base it does not spell out (`this.host + "/orders"`, with `this.host` set elsewhere) is not a route of the root when a call builds it under a prefix (`/rest/order-history/orders`): the call's row says where its base put it, and the root is not asked. A path of an API description written into a script (Swagger UI's `swaggerDoc`) is the description's, under its servers, read by `azhaq-openapi`. In every script it looks for:

- URL and path strings. Strings that name no route are dropped: pieces of a parser table or a minified name (`/pQ`, `/SQ`: one segment of one or two letters with a capital) and a package named after its owner (`/juice-shop/juice-shop`: a slug with a hyphen or a dot, twice). Short routes in lower case (`/v1`, `/me`, `/id`), a locale (`/en/US`) and a word twice (`/admin/admin`) are kept; a version prefix alone (`/v3`) is requested, and stays in the map only when something answers there;
- the requests scripts make through an HTTP client (`this.http.post(…)`, `$.get`), `fetch`, `XMLHttpRequest`, `$.ajax` and `axios`: the method, the path with run-time parts as `{name}`, and the query and body names. A request made inside a function that takes the URL as a parameter is read where the function is called, one level deep: `logQuery('/logger', …)` with `function logQuery(url, params){ fetch(url, {method: "post", …}) }` is `POST /logger`. The function's parameter defaults count (`method = "POST"`, also for a call that passes `undefined`), and so does a prefix it puts on the parameter before the request (`url = API_ROOT + url`); any other change to the parameter, or a name the script declares twice (`usersApi.request` and `ordersApi.request`), and the function is not followed. A request whose path has a placeholder for the parameter stays a route of its own (`/api/accounts/{id}` besides `/api/accounts/me`). A path relative to the page counts only for `fetch`, `XMLHttpRequest` and `$.ajax`, as without a helper, and jQuery sends a GET's `data` as its query. When a request's method is a value known only at run time, the route is listed without one;
- paths joined from constants where the request is made, such as `og+sg.LOGIN` with `og="identity/"` and `sg={LOGIN:"api/auth/login",…}`. A name counts only if the script binds it once, so a short minified name reused across modules is not guessed at. Placeholders such as `<videoId>` become `{videoId}`;
- GraphQL operation names, from query documents or the parsed form bundlers emit;
- the views of the app's router, from its route table: Angular (`{path:'admin', component: …, canActivate: [AdminGuard]}`, lazy `loadChildren` and `loadComponent`, `children` joined to their parent), React Router (`<Route path>` as written or as compiled, `createBrowserRouter`), Vue Router (`meta.requiresAuth`, `beforeEnter`). Whether the app routes by the hash (`useHash`, `withHashLocation`, `createWebHashHistory`, `HashRouter`, `mode: 'hash'`) decides their URLs: `http://host/#/administration`, else the path from the page's `<base href>`. They are `client-route` rows with their guard; a string that names a view is that view's, not a page to request. A view after the hash is never requested; one in the path is asked for once, since the server may answer it itself (a sign-in's 401, a page it renders), and keeps the server's role then, the guard noted beside it;
- WebSocket endpoints: `new WebSocket(…)` and `SockJS` with the URL worked out where the script builds it, `ws://` and `wss://` URLs, socket.io's `io(url, {path})` with its namespace, or socket.io's default `/socket.io` when the library is in the bundle and the app's call is not readable. They are `websocket` rows on the page's site, never requested, and their paths (`/socket.io`, `/engine.io`) are not pages;
- credentials: keys of AWS (with the secret key next to an access key id, which makes the pair high), Google, GitHub, GitLab, Slack, Discord and Slack webhooks, Stripe, SendGrid, Mailgun, Twilio, OpenAI and Anthropic; private keys; JWTs; variables bundlers inline (`REACT_APP_…`, `NEXT_PUBLIC_…`, `VITE_…`); and values of eight or more characters assigned to secret-sounding names, kept only when they look random (entropy) and not like a label or placeholder. Values are stored whole; the HTML report shortens them.

Well-known library builds served from the app's own origin (`react-dom.development.js`, `jquery-3.6.0.min.js`, `swagger-ui-bundle.js`) are not fetched: they are large and hold no routes of the app, only stray strings.

A script that names a source map, in its last line or in a `SourceMap` (or `X-SourceMap`) header, has the map read when the run may request it: the map is recorded with the app's own source files (libraries left out), and those sources are scanned like scripts. A script file that names none has `main.js.map` asked for next to `main.js`, for up to 10 scripts per origin, and kept only when it is a source map (JSON with `sources` and `mappings`; the observation that records it says `"guessed": true`). An exposed source map is worth knowing about on its own.

Build manifests list what a page's scripts do not name: Next.js's `_buildManifest.js` and `_ssgManifest.js` (asked for at `/_next/static/<buildId>/` when the page has Next.js's scripts and `__NEXT_DATA__`; its chunks are named from `/_next/`, its dynamic pages kept as templates, `/admin/users/[userId]` as `/admin/users/{userId}`, `[...slug]` as `{slug}`, and `/_app`, `/_error` left out), Create React App's `asset-manifest.json` (when the page loads `static/js/main.<hash>.js`), Vite's `.vite/manifest.json` and `manifest.json` (when a script carries Vite's preload helper), Angular's `ngsw.json` (when a script registers `ngsw-worker.js`), and Nuxt's build meta (`/_nuxt/builds/meta/<id>.json`, its prerendered pages and route rules). Each is asked for once per run; a JSON one is a `manifest` row, and the scripts it lists are read, its maps and pages kept.

Each route found in a script keeps where: the script's URL (the page's for an inline script, with the page's line numbers), the line and column, and up to 120 bytes of code: the call as written, or a string with what surrounds it, with credentials blanked (an inline script of a signed-in page can hold the session). Up to three places per route per page, calls first; a route read from a source map's original file names that file.

`azhaq-openapi` also reads a description written into a script, as Swagger UI's `swagger-ui-init.js` carries it.

### Crawling

`azhaq-crawl` reads each page's links from its markup and headers, and `crawl` is `run` with the subdomain, archive, certificate, RDAP and cloud collectors, the 32 path checks, the favicon and the source-map guesses (`main.js.map` next to a script that names none) turned off (`-sweep` turns them back on): it sends what a crawler sends, the pages it finds, the scripts they load and the routes they name.

- **Sinks.** `a` and `area` (`href`, `ping`), `link`, `base`, `iframe`, `frame`, `embed`, `img` (`src`, `srcset`, `dynsrc`, `longdesc`, `lowsrc`), `source` (`src`, `srcset`), `video` (`src`, `poster`), `audio`, `track`, `script` (`src`), `object` (`data`, `codebase`, `param` values that are paths), `applet`, `body`, `table`, `td` and `th` (`background`), `blockquote` and `q` (`cite`), `button` and `input` (`formaction`), `input type=image`, `html manifest`, a `<meta http-equiv=refresh>`, GET `form` actions, `hx-get`, and the `Link`, `Content-Location` and `Refresh` headers; then the URL-like strings of `javascript:` links, `on*` handlers and `data-*-url` attributes. `hx-post`, `hx-put` and `hx-patch` are listed as routes with their method and never asked. Where a URL was read (the tag, the attribute and the page) is kept for `-jsonl`. A page lists every link it has: nothing is cut at a number of links; the requests are bounded by the templates (`-per-template`) and by `-max-items`, which the summary reports when it stops the run.
- **Text.** katana's string patterns are read over every page, script and JSON answer (`internal/webextract/barestr.go`): a string that names a page of the application (`users.php`, `admin/`, `./notes/x.html`) is a URL, asked like a link. Every other string is kept as a rejected candidate with its reason (a media type, an expression or a template, a script or style file name, library code, another host, a link outside the crawl's scope, named in an error page, a pattern in `robots.txt`) and is never requested; `crawl -rejected` lists them and the summary counts them. A relative string is resolved against the page, as a browser does for a fetch; its reading against the script's own file, where that differs, is kept as a rejected candidate.
- **Scope.** A link is followed when `crawl`'s scope allows it: by default the registrable domain of the start URL and its subdomains (an address only itself, and only its port), then `-allow` and `-deny`. `-fs rdn|fqdn|dn|REGEX` picks katana's field scope, `-cs` and `-cos` are URL regexes, `-ns` removes the field scope. Links outside it are counted in the summary and listed by `-do`.
- **Forms.** Every form is a `forms` entry of its page. A GET form is asked once with neutral values in its fields (the page's own for hidden fields, ticked boxes and selects, `azhaq` for text, `azhaq@example.org` for an email, `1` for a number); `-no-form-fill` leaves it. A POST form is sent only with `-submit-forms`, with the same values, urlencoded: it changes data on the target, each submission is one request of the budget and the pace, is in the ledger, is held to `-allow`, `-deny` and the crawl's scope, is skipped when its address looks like it would change something (`logout`, `delete`, …) or when it uploads a file, and the summary says how many were sent and which were not.
- **Politeness.** `crawl` waits and asks again when a host answers 429 or 503 (1 s doubling to 30 s, or `Retry-After`, up to three times; the summary names the hosts and the requests that still got it), asks once more after a timeout or reset from a host that had answered, carries the cookies the target sets, and paces each host with `-hrl` besides `-rate`.

### Sessions and roles

`-cookie` and `-header` apply to every request of a run, and so does the session `-login` gets: Chrome fills and submits the login form, and the cookies the site sets and a JSON Web Token the page stores become a `Cookie` and an `Authorization` header (`internal/browser/login.go`). While a session is set, URLs that look like a logout are not requested, by the HTTP collectors or by `-browser`. A role of `azhaq roles` is headers (`-role`) or an account to sign in with (`-role-login`). `azhaq roles` runs the same seeds once per role, in turn, each with its own database. Then it replays: every URL any role reached (on the run's hosts, a GET whose name does not say it changes something) is asked with each role that did not reach it, through that role's session, and GET routes with path parameters are filled with the values of identifier-like fields (`id`, `username`, `*_id`, `*_title`, …) the roles' own JSON answers held: values given with `-id` first, then each role's own (a value only that role's answers held), then shared ones. Each endpoint then has an answer per role (status, length, body hash, nested JSON field paths, whether it is an error, which fields hold secrets), a 2xx that is not an error counts as reading it, and a verdict names the difference: anyone reads sensitive fields, a role reads another role's object, an object every signed-in role reads alike, roles read the same sensitive fields, the same answer for a role that never found the URL, signed-in only, only one role reads it, some roles refused, different fields, an object anyone reads, status differs, different data, the same for all.

The evidence of a roles run is a second database, `roles.db`, in its `-dir`. Its `meta` table records when the run saved it (`saved_at`), which `azhaq report` quotes as the run date; `azhaq report` (`cmd/azhaq/report_cmd.go`) reads it and sends nothing.

### Catch-all responses

Many applications answer every path: a single-page app serves its index for any route, some servers return a "not found" page with status 200, others redirect every unknown path to a login page. Without a check, each of those paths would look like a real page.

Before a non-root URL counts as visited, `fetch.CatchAll` compares its response with the answer for a random path in the same directory (`/rest/user/azhaq-…` for `/rest/user/login`). The responses match when the status is the same and either the redirect target or the body is the same once the requested path is removed from it, so error pages that echo the path still match. Bodies that differ only by a token or timestamp match on title, line count and word count. Each directory is probed once per run, up to 24 directories per origin.

A matching response is stored with `"catchall": true` and shown as `catchall` in the map. The crawler and the JavaScript reader skip such pages, and the path sweep drops them.

### Path checks

The built-in path checks (`azhaq-paths`, 32 paths per web service, `-no-paths` turns them off) include the places an API description sits: `openapi.json`, `swagger.json`, `api-docs`, `v3/api-docs`, `v2/api-docs`, `swagger/v1/swagger.json`, the YAML names, `api/openapi.json`, `api/swagger.json` and `swagger`, and under each API base the run found (`/rest/`, `/v3/`, up to 8 per origin) the same names again. Those are asked one at a time, likeliest first, and stop at the first answer that is an OpenAPI or Swagger document with paths, or the Swagger UI or ReDoc page that loads one. Once an origin has served a description (here or through `azhaq-openapi`), its other locations are not asked, and the summary says so: `path checks: 28 skipped (an API description was already found)`. Every other check is still asked: only a check whose answer is already known is skipped. A Swagger UI whose script carries the document (Juice Shop's `/api-docs/`) is read from that script, and the names next to it are not guessed.

A page that is byte for byte what the site root answers for a made-up path (a single-page app's shell) is the catch-all answer in a directory whose own baseline has not been asked, so that baseline is not requested; a directory with answers of its own is still asked. On Juice Shop a default `azhaq run` sends 148 requests, for the same 70 of 77 known routes.

## DNS

`internal/notify` sends messages and knows no target. `Client` is the one place a notification leaves from: a pace (`-rate-limit`, a token bucket), a timeout of 30 seconds a try, three tries on a 429, a 5xx or a connection that failed (`Retry-After` honoured up to a minute, doubling back-off otherwise), a redirect to another host refused, and the scrubbing of every error: a transport error is cut down to what went wrong (the `url.Error` that wraps the whole URL is not wrapped), and the request URL's path and query and every secret a provider registered (webhook URLs, tokens, keys, passwords, header values) are removed from the text of an error; of a failed answer only a bare error code (`channel_not_found`) is kept, since a server may echo anything. Providers (`slack`, `discord`, `pushover`, `googlechat`, `smtp`, `teams`, `telegram`, `custom`, `gotify`) read notify's `provider-config.yaml` and build the requests projectdiscovery/notify and its shoutrrr dependency build; `chunk.go` is notify's two splitters (one message per line, `-bulk`) and `Split` cuts a text to a service's limit for the webhooks of `watch`. `watch` sends through the same client and counts a delivery that failed as exit 3.

`internal/dnsr` resolves through a pool of recursive resolvers (six public ones by default). `-resolvers` is read by one parser, `dnsr.ParseResolvers`, for every command: a file with one resolver per line, or a comma list; a resolver is `ADDR`, `ADDR:PORT` (UDP), `udp:`, `tcp:`, `dot:` (DNS over TLS, port 853) or `doh:URL` (RFC 8484, POST, or `:get`) and its address. Queries go round robin, paced only by the queries in flight unless `-dns-rate` sets a rate per resolver; a resolver that leaves a third of its recent queries unanswered is asked one turn in sixteen until it answers again; a timeout, SERVFAIL or REFUSED moves the query to another resolver (`-retry` attempts, 3 by default), and every question carries an EDNS0 buffer of 4,096 bytes, as dnsx asks, so a long answer arrives over UDP; a truncated answer, or one larger than the buffer, is retried over TCP. `-proxy socks5://` sends every query over TCP through the proxy. Each name is resolved once per run. Special-use names (`localhost`, `*.test`, `*.local`) and single labels go to the system resolver instead, so `/etc/hosts` and local DNS still work; in `dns`, naming resolvers with `-r` sends every name to them, as dnsx does.

`azhaq dns` does not go through the engine. `Pool.Lookup` asks the record types the flags select, one question each, and keeps what the answers say in dnsx's `DNSData` shape (`dnsr.Data`); a bounded set of workers (`-t`, 100) takes names from the input as it is read, so a list of any size is asked in constant memory, and `-rl` paces names, not queries, as dnsx does. An A question whose answer has no address is put to a second resolver once before the name is called dead (`-retry 1` turns that off). `-axfr` connects over TCP to the name servers of the name, whose addresses it asks, and to the resolvers given, and only to those the scope allows. `-trace` asks the root servers and follows the delegations. With `-db` the names that have records are written to a workspace as `azhaq-dns` observations.

A name is a wildcard answer when one of its parent zones answers for random labels and the name's addresses, or its CNAME target, are what the random labels got. Each zone is probed once per run. Real hosts in a wildcard zone are kept when their addresses differ; a real host that shares the wildcard's address is dropped, the same trade-off other resolvers make.

## Subdomain sources

`azhaq-subdomains` asks every selected source at once and records each one's count, time, requests and error. crt.sh is asked again up to three times, after 1, 2 and 4 s, and not once 12 s have passed, since every other source waits for it. A source that answers 429 is asked again after its `Retry-After` (a pause of 2, 4 and 8 s when it gives none), at most three times and not for longer than 30 s; the row says how many requests were retried and whether the source gave up. Most sources are subfinder's source packages, run in-process: Azhaq supplies the HTTP client, a limiter with subfinder's per-source rates, and keys from the provider file. crt.sh, Cert Spotter (usable without a key: it then reads the first page of issuances and says so; with a key it pages with `after=` until a page is empty) and Chaos are implemented in Azhaq. An answer that is an error with a 200 status (a quota line such as hackertarget's `API count exceeded`, a JSON object holding an `error` or only a `message`, a page titled `Just a moment...`) is read as one, not as an empty list: a source that gave no names after one failed, with the server's words in its `error`. A source that needs a key is skipped, and listed as skipped, when none is configured. When every source that ran failed and nothing was found, the result is marked `degraded` rather than reported as zero.

The default set, keyless: anubis, certspotter, crt.sh, crtname, hackertarget, hudsonrock, rapiddns, scanmalware, shodanct, subdomain.center, thc; keyed sources join it when their key is configured. `-all-sources` adds slower ones. subdomain.center pads its answer with random names (a random 500 of about 6,300 for tesla.com per call): a name only it gave is kept when it resolves. Without a key it is asked again while its last round gave a name that resolves and no other source had, to 12 rounds; a round's new names are looked up (once each, one resolver's NXDOMAIN is enough) before the next round is asked, and with `-dns-rate` the guesses cost at most half what the other sources' names did, and not less than 1,000. Without `-live` the guesses are not looked up: the source is asked once and its names are listed unverified.

Azhaq also keeps the names it has kept for a domain in `names/DOMAIN.json` under `$AZHAQ_DATA_DIR`, else `$XDG_DATA_HOME/azhaq`, else `~/.local/share/azhaq` (first and last time seen and the sources that gave each, at most 200,000 per domain, the ones unseen the longest dropped first; written through a temporary file and a rename, a file that does not parse is set aside as `.bad`). The next run asks this file as a source called `history`, a source that, like subdomain.center, is verified: with `-live` a stored name counts only if it resolves now, so stale names drop out and a name a source missed this time comes back; without `-live` no lookup is made and the name is listed `unverified`. `-no-history` neither reads nor writes it. The payload's `coverage` (`observed`, `estimated`, `share`) is a Chao1 estimate over how many independent sources gave each name, which leaves out the verified sources, and a sampled source's row has `population_estimate`, a Schnabel estimate; [OUTPUT.md](OUTPUT.md#drop-in-commands) gives the formulas. Tests run `subs` offline with `subcol.UseTestSources`, which replaces the source list with fakes.

A domain the engine derives from a URL or hostname (`-url https://app.example.com/` implies `example.com`) gets 15 seconds per source instead of the usual bound (`-source-timeout`, 1 minute, for subdomain sources; 3 minutes for each archive), here and for historical URLs: the run is about the application, and one slow source would otherwise hold up its map. A domain given with `-domain` gets the full time. Sources that ignore their deadline are reported as timed out two seconds after it and no longer waited for.

## Path guessing

`-dirs FILE` (active; `@common` is the built-in SecLists `common.txt`, MIT, 4,750 words; the targets given are its scope unless `-allow` or `-scope` names one) guesses paths from where each URL given starts (the path it has, `/` for a bare host; a URL another collector found is swept only from the front page), then in each directory it finds, down to `-dirs-depth` levels. Before a directory is swept, it is asked for names that cannot exist, in the shapes ffuf's auto-calibration uses (a random word, `admin…`, `.htaccess…`, a random directory, and one per extension), at the sweep's pace and together (up to `-dirs-threads` at once, so a slow service is waited on for one round trip, not one per shape). A guess is dropped when it answers like one of those: same status and the same size; or, when the not-found answers differ in size among themselves, the same word and line counts; or, when their bodies or redirects repeat the path asked, a size that differs only by the length of the path, or a redirect that repeats it; or the same redirect. Statuses default to ffuf's (`200-299,301,302,307,401,403,405,500`); `-dirs-mc -dirs-ms -dirs-mw -dirs-ml -dirs-mr` and `-dirs-fc -dirs-fs -dirs-fw -dirs-fl -dirs-fr` are ffuf's matchers and filters (`internal/fuzz`'s, as `fuzz` uses them), applied before the calibration. A directory is a path that redirects to itself with a trailing slash.

The sweep has its own client: no cache, no redirects followed, bodies read only to count them (a body is kept, up to 1 MB, only for `-mr` and for the calibration's check that a page repeats its path), one connection kept per thread, 40 requests in flight and no pace beyond that, as ffuf (`-dirs-threads`, `-dirs-rate` to set one). Hits become URLs for the other collectors; a sweep hands them to the engine in batches, which write each batch in one transaction, so a target that answers every guess is not slowed by the workspace. With a session, logout-like words are skipped.

## Fuzzing

`azhaq fuzz` is not a collector: `internal/fuzz` is ffuf's engine, a request template with keywords (`FUZZ`, or `-w FILE:KEYWORD`) that can stand in the URL (host included), the method, the headers (`Host` too) and the body, wordlists (files, or the output of `-input-cmd`, made when the input is reached) run through it (clusterbomb, pitchfork, or sniper with `§` marks, which becomes one template for each marked place), encoders applied to the words (`encode.go`, in process), matchers and filters over the answers (status, size, words, lines, regexp, time to the first byte), auto-calibration (strategies, per host with `-ach`) and recursion (redirect-based or greedy, a queue of jobs, each with an optional time limit). Counts (words are spaces plus one, lines newlines plus one, the body decoded when the server compressed it), the match rules and the calibration follow ffuf 2.3, so a command line moved from ffuf gives the same results; a command line that gives its own filters does not calibrate. Sending is behind `fuzz.Sender`, so the engine runs against a fake in tests; the real one sends through `internal/fetch`, so every request spends the run's budget, is paced by `-rate`, goes in the ledger and stops at the kill file. `-replay-proxy` copies go through a second client that has no ledger, budget or pace: it is the user's proxy, not a target. The host of `-u` is the scope unless `-allow`, `-deny` or `-scope` say otherwise (`FUZZ.example.com` gives `example.com`); an input whose host is outside it is not sent and is counted in the summary. Five requests in a row to an origin with no answer stop the run (`-se`, `-se-after`, `-sf`, `-sa` change what stops it). The run keeps where a stopped one goes on from in a high-water mark and the few answers past it, not one flag for each input of the product, so two 300,000-word lists in clusterbomb need no memory for the product. `-control FILE` reads lines added to a file while the run goes (pause, rate, filters, queue). Preflight and postflight files (`flight.go`) wrap the sender: each request file is sent through the same client (budget, pace, ledger, scope), values are read by regexp or by form field, meta tag, cookie or header, and a value that would change a request's scheme, host or port is refused. Reports (`report.go`) follow ffuf's files; with `-db`, the matches go into the workspace as ffuf's do.

## Parameters

`-params FILE` (active; the targets given are its scope unless `-allow` or `-scope` names one) looks for query parameters each page reads but does not link, the way arjun does. FILE is a wordlist or one of `small` (1,000 names), `medium` (3,000) or `large` (6,500, the default of the `params` command), built into the binary: SecLists' `Discovery/Web-Content/burp-parameter-names.txt` (MIT, Copyright (c) 2018 Daniel Miessler, licence kept in `internal/collectors/paramcol/data/LICENSE-SecLists`) and names Azhaq's own passes found (query strings of archived URLs, forms and API bodies of its lab apps), the likelier first. The page is asked twice with one random name: that answer is the reference, and the difference between the two is the page's own noise (a page that changes too much by itself, is not text, HTML, JSON or XML, or answers 405 to a body method is left alone, and the summary says why). Names the reference answer itself holds (the `name` and `id` of its form fields, the variables its scripts set empty, the keys of its objects, the words of a short plain reply) go first. It is then asked once with as many random names as a group holds. Names go out in groups of at most 500 names and, in a query, about 7.6 KB, each with a random value; a server that answers the crowd with another status (a query too long) is asked with fewer names until it answers as it did for one, and that size, in names and bytes, is the group size for the page. Up to 5 groups are in flight at once (`-params-threads`; `params -t`); the rate limit (`-rate`) is shared by all of them. A request whose answer differs from the reference by status, by size beyond the noise, by its header names, by the path of its `Location`, by its line count beyond the noise, by carrying one of the values back, or by printing a name of 5 or more characters between quotes or spaces that the reference does not, marks its group, which is halved until single names remain; when the first half of a flagged group changes nothing, the second is split without being asked first, a name found by size, status, headers, location or lines is confirmed with one more request, and a reflected value or a printed name names its parameter directly (a printed name is asked once alone). A page that answers the random crowd otherwise than one (an error page that prints the query string back, a server that refuses a long query) is judged against controls instead: a group whose answer differs from the reference is asked again with random names of the same lengths and random values, and only what that control does not show counts. A value counts as reflected when it comes back more often than the control's values do, a size is compared with the values taken out of both answers, and a group whose control gets another status too (414 for a long query) is split without being searched, and so are the groups that come after it. When most names of a group, or nearly every name tried alone, change the answer, as many random names made like them (letters, as long) are asked once: if they change nothing, the page reads those names (a short list taken from its own scripts) and they are kept. If they change it too, the page answers names it does not read: that group's names are dropped, the search stops there, and a note says so (`… answers names it does not read (16 of 16 names tried changed the answer): not searched for parameters`, or `not searched further` when earlier groups found names, which stay). After the list, about 70 toggle names (`debug`, `test`, `admin`, `verbose`, `source`…) not found yet are asked once with each of the values `1`, `true`, `yes` and `on`, one request per value: a page that reads `debug` only when it is `true` is found, and the row says which value (`values`). Nothing is dropped without a word: a 429, 418 or 503 that the page did not give for unknown names before is waited out (its `Retry-After` up to 30 s, else 1, 2 and 4 s; every request to that host waits) and, if it persists, the page fails with the names found so far kept and a note (exit 3); a request that gets no answer, even after one retry of a timeout, fails the page the same way, and the names of its group are not judged; a page left alone (it changes by itself, is not text, has more pages than `-params-per-host`) is named in a note. A request that times out is asked again with 5 s more, up to 20 s (`params -T`); `params -d SECONDS` waits before each request, one at a time, and `-stable` is one at a time with 3 to 9 s before each and 30 s after a refused connection. GET by default. `-params-method POST`, `JSON` or `XML` (`params -X`) send the names in a form, a JSON object or an XML document instead, 500 at most per request: a request that may change data on the target, so it is refused unless `-params-writes` is given and `-allow` or `-scope` names the targets (or there is one target); every request is counted in the budget, paced and in the ledger, the page's row says how many were sent (`writes`), and the summary says writes were sent. A name that cannot be an XML element is not sent and is counted in a note. `-params-include` is sent with every request (for a body, a form, a JSON object, or XML, or a template with `$arjun$` where the names go). At most 20 pages per host (`-params-per-host`); there is no pace unless `-params-rate` (per host) or `-rate` is given.

## Networks

`-asn` seeds an autonomous system: `azhaq-asn` lists the prefixes it announces (RIPEstat, no key) and the holder's name. `-cidr` seeds a range directly. `azhaq-prefix` expands IPv4 prefixes into addresses, at most `-max-ips` (4,096) for the whole run, and says so when a range is cut short. Each address gets a reverse DNS lookup (`azhaq-ptr`), an HTTP probe and a TLS handshake without SNI; names in reverse DNS and on certificates become hostnames to resolve and probe. Reverse names a provider derives from the address (`ec2-192-0-2-7…`, `7.2.0.192.static…`) and shared platforms are recorded but not followed, and names found this way are not enumerated as domains: on shared hosting they may belong to neighbours. Ask for a domain with `-domain`.

## Rendering pages

Static extraction reads what scripts contain; `-browser` also runs them. `azhaq-render` loads pages (not scripts, assets or API routes) in the run's Chrome, up to 30 per host, and records every same-origin request the page sends while it loads, which for a single-page app are its API calls with their real paths and query strings, and the links and forms of the document once rendered. A page read this way is loaded without its images, fonts and media, socket.io's polling and the tab's icon (not sent, not counted: they name no route; a request to a host outside the scope is still listed), which a screenshot has. Those become URLs for the other collectors. The writes a page sends (a POST, a DELETE, a beacon) are not sent but mapped, with their method and names (see [Chrome and the scope](#chrome-and-the-scope)). It shares the browser, tab limit and session headers with screenshots.

`-interact` (with `-browser`) clicks each rendered page's buttons, links, tabs and menus, up to `-interact-clicks` (12) of them, putting the page back after each (by history, else by loading it again). It finds what only a click brings: the requests a click's script sends (the API calls), the route the address goes to (a path after `pushState`, a route after the hash, which is a `client-route` row), and the links the changed page shows. A click sends nothing a page load does not: the writes it would send are refused and mapped like any other (`-browser-writes` is a separate choice), a button or link whose words or address say log out, sign out, delete, remove, reset or the like is not clicked, `mailto:`, `tel:`, `javascript:` and downloads are not, and Chrome stays held to the scope and the budget. The summary says how many clicks were made on how many pages, how many routes they found, how many candidates were left alone and how many writes were mapped. Azhaq does not attach to a Chrome that is already running (katana's `-cwu`): a Chrome it did not start would not be behind the scope guard and the ledger.

Without `-browser`, the crawler reads what a page leaves for its scripts to render where it can: links written in Markdown in the page's text (`[User Search](/app/usersearch)`, which a converter such as showdown turns into links in the browser) are followed like links. It also notes `{{templates}}` in the text and an empty shell (a mount point such as `<div id="root">` or `<app-root>`, scripts, and next to no text). The run's summary suggests `-browser` when a page of the target carries Markdown links, three or more template expressions, or is an empty shell while the map of its origin has fewer than 10 routes; a server-built site, or a single-page app whose scripts gave up their routes, gets no suggestion.

## Chrome and the scope

Chrome (`-browser`, `-screenshots`, `-login`, `-role-login`) goes only where the run's own requests may (`internal/browser/scope.go`). When it starts, every request of the browser, from pages, frames, workers and service workers alike, is paused through the DevTools Fetch domain, enabled for the whole browser before any tab opens. A request is sent on when its host is in the scope (the predicate the HTTP client uses, `fetch.Allow`), or, without a scope, in the site (`fetch.Site`: the registrable domain, or the address) of a page Chrome was pointed at, as a redirect without a scope is followed. Any other is failed (`BlockedByClient`) before it leaves the machine; `data:`, `blob:` and `about:` URLs pass, as nothing is sent. What connects without a request the Fetch domain sees (a WebSocket, a preconnect, Chrome's own update and sign-in services) is stopped by a SOCKS5 proxy on loopback that Chrome makes every connection through, loopback ones too, and that connects only to hosts the same predicate admits (`internal/browser/guard.go`). It connects once Chrome has sent its first bytes, as the run's own requests would: TLS through the environment's `HTTPS_PROXY`, plain HTTP through `HTTP_PROXY`, whatever the port, or directly with the run's DNS answers. Those bytes also tell a WebSocket's handshake (a request asking for the upgrade, or a TLS hello offering HTTP/1.1 only, which Chrome sends for WebSockets alone), which the guard counts and paces, and refuses once the budget is spent. A WebSocket over an HTTP/2 connection Chrome already has (RFC 8441) is not seen. WebRTC is kept from sending UDP outside the proxy. A window a page opens (`window.open`, a link or a form to `_blank`) is closed as it opens: it would outlive its page, unpaced.

Chrome cannot authenticate to a SOCKS proxy, so the guard checks who connects. On Linux it relays only for the Chrome it was started for: the socket at the other end of each connection is looked up in `/proc/net/tcp` and must be held open by Chrome's browser process or one it started (`/proc/PID/fd`); a socket of another user, or one another process holds, is refused. Where it cannot tell (`/proc/net` or Chrome's processes cannot be read: a hardened system, a confined Chrome), and on other systems, another local process may use it, to hosts in the scope, while that Chrome runs: what it sends then is neither counted nor paced. The guard listens on a random loopback port, starts with Chrome and stops with it.

Chrome sends GET, HEAD and OPTIONS (a CORS preflight) only. Any other method a page, a frame or a worker sends (a `fetch` or an XHR that POSTs, PUTs, PATCHes or DELETEs, a beacon, which is a POST, a form a script submits with POST) is paused like every request and failed (`BlockedByClient`) before it leaves, uncounted (`internal/browser/writes.go`): a page that tracks, saves or deletes as it loads would otherwise change data on the target behind a run that only maps. The sign-in is the exception: until the session is read, the tab of `-login` and `-role-login` sends every method it would, not only its form or XHR call with the credentials but whatever else the page's own scripts send meanwhile (Juice Shop's sign-in page, for one, opens a socket whose polling sends `POST /socket.io/…`) — all counted, paced and in the ledger, same as any other request; the pages after it do not. What a refused write would have sent is not lost: its method, the names in its query and the names its body sends (a JSON object's keys, also in a beacon's `text/plain` string; a urlencoded or multipart form's fields; never a value) become an operation on its route with `source` `browser`, as a script's call does, so the route is in the map as a `hint` with that method and in the OpenAPI export; it is not fetched for it. The summary lists it as left alone, by method and URL without its query: `{"target":"POST http://127.0.0.1:3001/api/track","reason":"a page's script would send a write"}`. A form a script posts is stopped as a user stops a navigation (`Aborted`): the page stays as it was, and its links, forms and screenshot are its own, not Chrome's error page. `-browser-writes` lets every page send its writes as a user's browser would, still inside the scope and the budget: they change data on the target. They are mapped alike and not listed.

What Chrome was refused is listed in the run's summary as skips, without its query string: `{"target":"http://localhost:8897/ext.js","reason":"outside the scope (Chrome)"}` (`outside the site (Chrome)` without a scope), on the page that asked for it, the first 100 URLs of the run; a note gives the number of requests when there were more. What no page claims is listed at the end of the run without one: a service worker's requests, a beacon a page sends as its tab closes (once per URL), and the refusals of a capped page, which is dropped to be loaded again; a write among those is listed, not mapped. A page that went outside the scope (a redirect, a script setting `location`) is not read and its screenshot not taken: what it shows is Chrome's error. A sign-in that goes to an identity provider outside the scope fails and names it: `the sign-in went to sso.example.com, outside the scope: add it with -allow sso.example.com`.

Chrome saves nothing to disk (`internal/browser/downloads.go`). Every download is denied for the whole browser (`Browser.setDownloadBehavior`, before the first tab opens): a URL that is a file (an archive, a key store, a program), an `<a download>` a page clicks as it loads, an answer with `Content-Disposition: attachment`. The request itself was sent, in the scope, paced and counted like any other; only what it answered is dropped, and nothing lands in the user's Downloads folder. Each refused download is listed like a request outside the scope, under `Chrome would download it`, as its URL without the query and the name Chrome would have saved it under: `{"target":"http://127.0.0.1:3001/ftp/incident-support.kdbx (incident-support.kdbx)","reason":"Chrome would download it"}`, on the page that began it, or at the end of the run for the sign-in's.

## Screenshots

`-screenshots DIR` starts one headless Chrome found on the machine (`AZHAQ_CHROME`, or `google-chrome`, `chromium` on the path) and drives it over the DevTools protocol (chromedp). Each web service's front page opens in its own tab, six at a time (`-tabs`), with the run's `-cookie` and `-header` values. The load event gets 15 seconds; a page that never finishes loading is captured as far as it got, 1.5 seconds after navigation, within 30 seconds. With `-rate` those times run from when the page last moved (a request of it let go, an answer heard), not from when it started, and tabs open only as many at once as the pace can fund (`-rate` times 30 s, over the requests a page makes): a page of 40 requests at 2 a second takes 20 seconds and is whole. After the wait, the picture is taken once nothing of the page waits for its turn and nothing it shows (images, styles, scripts, fonts, media, frames) is still on its way, for 0.3 s (under a pace, 0.7 s and one pace interval), up to 5 s more (under a pace, up to three times `-shot-timeout`): a single-page app asks for its images only after a script's request has been answered, and at a low rate that comes seconds after the load event. A script's own requests that stay open (a long poll) are not waited for. A picture taken while some of the page's images, styles or scripts had not come back, or while requests of the page still waited for their turn, is saved as `partial`, with a note, and the run exits 3. The tab's `/favicon.ico` is not fetched, a dialog (`alert`, `confirm`, `beforeunload`) is accepted, and Chrome may open the ports it refuses by default (`-unsafe-ports`).

What a screenshot is: `-shot-size WxH` (default 1440x900), `-shot-fullpage` (up to 16384 pixels tall), `-shot-wait` after the load event (default 1.5 s), `-shot-timeout` (30 s; with `-rate`, how long a page may go without moving), `-shot-format png|jpeg` and `-shot-quality`, `-shot-js FILE` (run on the page before the picture: it runs on the target's page), `-shot-codes 200,301` (take only pages that answered so; the others get a note), `-shot-html` (keep the rendered page). Chrome: `-chrome PATH`, `-chrome-proxy URL` (http or socks5, for Chrome's own connections; the run's own requests use the environment's), `-chrome-profile DIR` (a user data directory, kept: sessions in it go with the pages; they are the target's only if the scope says so). The run's `-H` and `-cookie` values and its user agent go with every request.

What a run takes as targets (`shots`): URLs (path and query kept), hosts, `host:port`, address ranges (`192.0.2.0/28`, up to `-max-ips`), `-p` ports (numbers, ranges, `small` 80 and 443, `medium`, `large`), `-no-http`, `-no-https`, `-random`, `-nmap FILE` (an `nmap -oX` file: open web services; `-service`, `-hostnames`) and `-nessus FILE`. A name with several ports is a picture per web port that answers; a name with no port is tried on https, then http, and shot once.

What Chrome saw of each page is in its row (headers, TLS, technologies, console, network log: the `shots` row of OUTPUT.md); it is read from events Chrome sends anyway. `export -format html` embeds each picture, 560 pixels wide, in the one file. The PNG goes to `DIR/scheme_host_port.png`, and a 64-bit perceptual hash goes with it (`p:` and 16 hex digits: a discrete cosine transform of the picture, as `pHash` is): the HTML export groups pages whose hashes are at most 10 bits apart from any member of the group, so thirty copies of one login portal are one row, and a login form, the nginx default page and an admin page are three. A hash from an earlier run has no `p:` and is not compared with these. A name and its URL are one page and are taken once. A page's images, scripts and styles each count against `-max-requests`: when too few are left, Chrome is refused them, no image is saved, and a note says what the page needs and what was left (`screenshot of URL not taken: the page needs about 26 requests and 8 were left (raise -max-requests)`; the figure is how many requests the page made when it was cut short). A run starts one Chrome and opens up to 6 tabs in it at once (`-tabs N`); each page is a tab, not a browser.

`azhaq gallery` (`internal/gallery`) is the interactive view of those rows. It opens each workspace read-only, reads every `azhaq-shots` screenshot row once into an index (a page's URL, title, status, technologies, headers as text, hash and file paths; the newest row of a URL stands for it), groups the hashes with the same rule as the HTML export (`shotcol.Cluster`, 10 bits), and sorts the pages once per order, so a filter is a pass over memory. The long parts of a row (network log, console) stay in the database until a detail view reads them. The text of kept pages (`-shot-html`) is read into the search in the background. Pictures are found from the row's `file_path`, `file`, or beside the database, only a PNG or JPEG is served, and thumbnails are made on first request and kept in memory. The page and its script and style are embedded (`go:embed`) and served from the same address under a policy that lets the browser load nothing else. The package has no HTTP client and opens no connection but the one it listens on; a test drives every endpoint with the pages' URLs pointing at a counting listener and asserts it was never reached.

## Ports

`-ports` (active; the targets given are its scope unless `-allow` or `-scope` names one) scans hosts in scope with full TCP connects, so it needs no root and leaves complete handshakes in the target's logs, like `naabu -scan-type c`. Lists are nmap's top 100 or top 1000 TCP ports (as naabu ships them), `full`, or ranges. Connection attempts share one rate across all hosts (`-port-rate`, default 1500 per second, naabu's for a connect scan; this machine's loopback is not paced unless it is given), as many in flight as the rate allows (up to 20,000 and the process's file limit; `-port-workers`), 1.5 seconds each (`-port-timeout`). A name resolves to at most two IPv4 and two IPv6 addresses (`-port-all-ips` for all, `-port-ip 4|6` for one family) with the A and AAAA queries only, and each address is scanned once however many names point to it. A `Prefix` seed is scanned by `azhaq-ports` itself, address by address in blocks of 256, without expanding it into seeds or asking reverse DNS, so a range has no size cap; the addresses that answer are followed by the other collectors. The ports of a host are asked in tiers (`-port-order random`: nmap's top 100, the rest of its top 1000, the others, each tier shuffled by a seed). A port that did not answer is asked again by the rule of `-port-retries`. `-port-discover first|only` asks each address a connect to 80 and 443 first. An address in a CDN or WAF range gets ports 80, 443, 8080 and 8443 only: the edge answers for thousands of customers; `-port-cdn-full` lifts that. The scan type is the scanner's `Detect` and dial functions; there is no raw scan.

An open port is read for 1.5 seconds: the first line a service sends (`SSH-2.0-…`, `220 … ESMTP`, a Telnet option negotiation, an IRC `NOTICE AUTH`) names it; binary greetings are marked as such. Ports that stay silent or answer like HTTP become URLs for `azhaq-http`, HTTPS first. The greeting, the HTTP head (`Server`, `X-Powered-By`) and, for a web port whose head names no product (or refused the HEAD with a 405 or 501), a `GET /` for a small JSON or text body, or an HTML page's title and generator, also give `product` and `version` (`internal/portscan/services.go`).

A port that stays silent is identified by what it answers (`internal/portscan/identify.go`; the protocols are in `proto_db.go`, `proto_msg.go`, `proto_dir.go` and `proto_net.go`, each written from its public specification, named in a comment). The steps, each a connect that is paced, counted by `fetch.Take` and recorded in the ledger: the request of a protocol whose usual port this is, on the connection already open; the `HEAD /`; for an answer that is not text, a TLS handshake (a greeting inside the tunnel is read before the `HEAD`, so IMAPS, POP3S, SMTPS and LDAPS are named); then one request of each of the remaining protocols on a connection of its own, the likeliest first (Redis, PostgreSQL, MongoDB, memcached, MQTT, AMQP, DNS over TCP, LDAP, SMB, SQL Server, Kafka, RDP, ZooKeeper, Cassandra, Oracle TNS, SIP, RTSP, SOCKS5, X11, STOMP, XMPP). The first answer a protocol's reader recognises ends it. An open port costs at most 24 connects after the first; a request waits twenty round trips (at least half a second, at most the banner wait) for its answer. After six open ports of one address that no request could name, the rest of that address's silent ports are not run down the list, and the row's `unprobed` and the summary count them (a firewall that accepts every connect would otherwise cost thousands). A request carries no credential and changes nothing; the raw printing ports (9100–9107) are never asked anything, and a port that closes the connection without a word is `tcpwrapped`.

`-ports-udp` (`ports -udp`, `-pu`) asks UDP ports on the same addresses (`internal/portscan/udp.go`): each port gets one datagram on a connected socket, the harmless request of the protocol the port usually carries (`internal/portscan/udp_proto.go`, `udp_proto2.go`: DNS, NTP, SNMP v1 and v3, SSDP, mDNS, NetBIOS, IKE, STUN, memcached, BACnet, CoAP, TFTP, rpcbind, the SQL Server Browser, SIP, NAT-PMP, Ubiquiti discovery, ASF-RMCP; for the rest a DNS query, then an SNMP get, then memcached's version, then an empty datagram), and the kernel turns an ICMP port unreachable into `ECONNREFUSED`. TFTP answers from a port of its own, so it is read on a socket that is not connected (on Linux with `IP_RECVERR`, so a refusal still reaches it). A reply is `open` (with what it names), a refusal `closed` (only an ICMP unreachable for that port says so; silence never does), and a port that stayed silent is asked again, every way its protocol has, before it is `open|filtered`. A host that refused some ports and answered nothing on a few others is probably rate-limiting its ICMP replies (Linux sends about one a second): up to 80 such silent ports are asked again one at a time at that pace, and more are left `open|filtered` and counted in `udp_limited` and the summary. Loopback is not rate-limited and is not paced. Each datagram takes `fetch.Take`, is paced and goes in the ledger as `udp`; an address in a CDN or WAF range is not asked. The `ports` row keeps `udp_open`, `udp_open_filtered`, `udp_closed`, `udp_scanned`, `udp_limited`, `udp_unlisted` (silent ports past 64 on one address, which `udp_services` then leaves out) and `udp_services`; the range row counts the addresses of a range that answered no UDP port (`udp_silent_addresses`, `udp_silent_ports`) instead of a row each.

## Historical URLs

`azhaq-urls` asks every archive at once for the URLs of a domain, and of its subdomains unless the run asks for the host alone (`urls` does by default, as gau; `run` asks for the subdomains), and records each one's count, pages, time and error:

- the Wayback Machine's CDX API, page by page (`showNumPages`, then each page), one request per second;
- Common Crawl's newest index, paged the same way;
- AlienVault OTX's URL list, 500 per page;
- urlscan.io's search, 100 per page (a key from the provider file raises the limits);
- arquivo.pt, one request; it often serves what the Wayback Machine refuses.

A 429 or 503 is asked again after the server's `Retry-After` (seconds or a date, however long it is) or, when it names none, after 2, 5, 10, 20 and then 30 seconds, for as long as the archive's time (`-urls-timeout`, 3 minutes) and the run's `-timeout` allow; a network error (a refused or dropped connection) is asked again 3 times with the same waits. `-urls-retries N` makes both a count instead. A wait longer than the time left ends the request at once with the reason (`failed after 2 tries, 429 Too Many Requests, Retry-After 2m0s; the 2m0s to wait is more than the 45s left`), not at the deadline with a bare timeout. A source that still fails stops, keeps the pages it read and is reported with its tries and the server's words (`failed after 4 tries, 429 Too Many Requests`); its row has `requests`, `retried` and `waited_seconds`, and the summary says what each archive gave. Each source has 3 minutes (`-urls-timeout`) and 50 pages (`-urls-pages`; a source that stops there is marked `capped`), with a pause between its requests (`-urls-pause`). The run's own `-timeout` ends the sources a few seconds before it, so their summary is still recorded, marked as cut short. The Wayback Machine, Common Crawl and arquivo.pt are sent the status, type and date filters (`-mc -fc -mt -ft -from -to`) in the query, as gau sends them; urlscan.io takes dates; OTX takes none, so a run that gives a filter it cannot apply does not ask it. OTX is asked as a hostname for a name with a subdomain and as its registered domain for `-subs`, as gau does. Any failed source marks the result `degraded`, so a refused archive never reads as "no URLs". A 200 whose body is an error (a quota line, a JSON `error`) is a refusal too (`web.archive.org answered 200 with an error, not URLs: …`); an empty answer or Common Crawl's `No Captures found` is not. The URLs are grouped by template; pages are listed first and at most 40 of them go on as hints, which the scheduler requests after the application's own pages. Static assets are listed after the pages, marked `asset`, and never requested: a file by its extension, one whose extension sits on an earlier path segment (`/x_original.png/<hash>`), one an archive cut short of its extension (`photo.?123`), and anything on a host whose first label says it serves media (`photos`, `images`, `static`, `cdn`, `fonts`, …).

URLs are normalized, kept when they belong to the domain (the host alone, or its subdomains too), and deduplicated; a URL on the domain that is junk (a scanner's payload or probe kept by an archive, a script's `NaN`, a link cut at its sentence's end) is left out and counted by reason in the summary's `junk`; `-urls-blacklist` and `-urls-fp` leave some out by extension and by host and path. `-urls FILE` receives all of them, and is written whatever ended the run. The `urls` command hands the collector a function that is called for each new URL as its page arrives, which is how it prints before the slowest archive has answered; `-urls-raw` hands it every row as the archive gave it. The graph receives the summary and one URL per template (`/product?id={v}` stands for every product page), parameters, API routes and server-side pages first, at most 200 per domain; the first 40 are fetched when the run is not passive. Static assets are counted and left out of the graph.

## Storage

The graph lives in SQLite through `modernc.org/sqlite`, a pure-Go driver, so the binary builds without CGO. Each run gets its own file unless `-db` or `AZHAQ_DB` names one. Every run has its own ID, and the store records which entities and edges each run saw. `azhaq diff` compares two runs from that record.

A database can hold many runs: `-db FILE` on every run of a target makes it a workspace. Work is deduplicated within a run, not across runs, so each run collects afresh; reads during a run see only that run's entities, observations and edges, while `export` sees all of them with their first and last sighting. After a run into a workspace, and with `azhaq diff -db FILE`, the last two runs are compared.

Diffs compare facts, not bytes: body hashes and sizes, response times, the address that answered, the session a run was given, each subdomain source's timing, and response header values (rate-limit counters, request IDs) are left out, while header names, statuses, titles and everything else count. Each database records the seeds it was run with. After a run, the CLI diffs against the previous run of the same seeds in the current directory (tracked in `.azhaq-index`), and `azhaq diff` on two runs with different seeds says so before the result.

## The map

`azhaq run` prints the graph as a ranked map: the seed host, live application pages, auth-gated URLs, APIs, other pages, then hints and fan-out. Each URL row has a coverage and a role.

| Coverage | Meaning |
| --- | --- |
| `visited` | fetched, and the response is the URL's own |
| `catchall` | fetched, but the answer is the one any path gets |
| `error` | requested, no answer (timeout, refused, reset) |
| `gone` | requested, answered 404 or 410: found in an archive or a link, not there now |
| `hint` | found (in a link, script, archive or API description) but not fetched; also a route scripts call only with POST or PUT whose GET answers like an unknown path, and a route only scripts name, with no GET call among them, whose GET answers 404 |
| `skipped` | found (in a link, script, archive or API description), and deliberately not requested: its name says a GET would change something (`word` names the verb) |
| `capped` | left over when the run hit its item, request or depth limit, or when its origin stopped answering |

Roles: `app` (the site root), `auth` (401), `forbidden` (403), `api`, `page`, `script`, `asset`. Routes list their methods, and below the row, each operation with its query names and body fields, from API descriptions and from the calls scripts make. A GraphQL endpoint read with `-graphql` keeps the whole introspection result (types, fields, arguments, input objects, enums, directives); its row lists each query, mutation and subscription with its signature (`query pastes(public: Boolean, limit: Int): [PasteObject]`), and `azhaq export -format graphql` or `-format sdl` writes the schema. A run that found an endpoint and did not introspect it (no `-graphql`, or its host outside the scope) suggests the run that would: `next: azhaq run -url ORIGIN/ -graphql -allow HOST …`. Hostnames are `live` (a seed host), `sibling`, `unresolved` (from a source or a list, not looked up), `dead` (no address) or `wildcard`; dead, wildcard and unresolved names are folded into one summary line each.

### What is requested

A found URL is requested with GET when it is on the run's hosts and in scope, has no unfilled parameter, and its path (or an `action=` value) does not start with a verb that does something: logout, delete, remove, reset, create, save, update, change, send, run, import, … (`webextract.StateChanging`). Those are kept as `skipped`, with the word, and listed under `left alone` in the summary, whatever found them: a link, a script's call, an API description; `-all-gets` requests them too. API description operations are asked when they are GETs that need no path or query parameter; the same verbs keep them out (VAmPI's `GET /createdb` resets its database). With a session (`-cookie`, an `Authorization` header, a header that carries a token), path and parameter guesses that read that way are not sent either, and are listed as `skipped`. Junk that is not a URL never enters the graph: path segments such as `NaN` or `undefined` from a script that ran without its data, links cut short in archives, dot segments a browser would have resolved (`http://site/..`), and URLs that carry a scanner's payload (path traversal, `/etc/passwd`, command or template injection, SQL, `<script>`, out-of-band callback domains such as `oast.live`), decoded twice since archives keep them encoded, or a scanner's own marks that an archive kept: its test files and tagged parameters (`acunetix_xsl_inclusion_test.xsl`, `netsparker(0).txt`, `?invicti=`, `nessus_test`, `bxss.me`, `xss.rocks`) and a random-named executable at the root (`/7zSo1DIz.exe`: letters and digits with a digit and the case changing twice; `Setup64.exe` and `winrar.exe` stay) (`webextract.Payload`). Nothing can replay what is not stored.

A run keeps the answers it gets (`responses` in the workspace, bodies gzipped) and the guesses `dirs` made, and the owner of each piece of once-per-run work (the built-in path sweep of an origin, `catalog.Claim`). `azhaq resume` reads them back: what the stopped run asked is not asked again or counted, and the same task does the same sweep. They are dropped once the run has nothing left to resume.

Requests to targets carry a current browser's User-Agent (CDN bot managers hold other requests open without an answer) and connect to the addresses the run's own resolver found for the name, IPv6 first where the machine has a route for it and IPv4 alongside after 300 ms, so `host_ip` is always one of the name's addresses. Third-party sources get `azhaq/VERSION` as User-Agent. A wordlist sweep (`dirs`, `fuzz`) sends ffuf's headers besides: no `Accept` (`fetch.ApplySweepHeaders`), so a server that negotiates its answer by it gives the size ffuf counts.

Rows that share a URL template are folded into one line with a count. Forms appear indented under the first row that has them, with their method, action (a form whose action is empty submits to its own page, one whose action is `#` to the page's `<base href>` or its own page without one; links and actions resolve against `<base href>` as browsers do, and on a route after a `#` the page is the app's front page), `multipart` for a multipart POST, and field names, followed by the query names of the URL itself; the query names of a page's links are on the links' rows. `azhaq export` keeps every entity unfolded and adds `template`, `methods`, `params` and `forms` fields.

## Connectors

Data Azhaq should not collect itself, such as paid internet indexes, comes in through connectors. A connector is a separate program that reads seeds on stdin and writes JSONL facts on stdout. It runs out of process, so its SDK, API keys and terms of service never become part of Azhaq. See [CONNECTOR.md](CONNECTOR.md).

## Design choices

- **In-process collectors, no wrapped tools.** Collectors speak their protocols directly or use permissively licensed Go libraries in-process (subfinder's source packages for subdomain sources, miekg/dns for DNS, wappalyzergo's matcher and cdncheck for fingerprints). Azhaq never shells out to subfinder, dnsx or similar tools, so every fact lands in one graph with its source. CI fails on GPL, AGPL, SSPL or unknown licenses.
- **Go.** Recon is I/O-bound. Go gives one static binary, cheap concurrency and a small memory footprint, and it embeds easily as a library in a worker process. Start-up work is kept small: the CDN and WAF ranges are read the first time an address is checked (`internal/cdnranges`), and the patterns of `internal/webextract` compile when first used, so `azhaq version` runs in about 16 MB.
- **A browser only when asked.** JavaScript routes are extracted from script text, which covers bundled single-page apps. `-browser`, `-screenshots` and `-login` drive a Chrome already installed on the machine; Azhaq downloads none, and that Chrome saves nothing to disk. Chrome is held to the run's scope and budget like every other request.
- **Map only.** Azhaq records what exists. It sends no payloads and does not test for vulnerabilities. Every request to a target is a GET, except `crawl -submit-forms` (POST forms, which change data), `params -X` (names in a body), `probe -x`, `-body` and `-rr`, which send the methods, body or request you give (they can change data on the target, are counted, paced and in the ledger, and the summary says they were sent), the sign-in tab of `-login` and `-role-login`, which sends every method until the session is read (its own sign-in request and whatever else the page's scripts send meanwhile), GraphQL introspection (a POST) with `-graphql`, what `-browser-writes` and `roles -replay-writes` send when asked for, the connects, one `HEAD /` or protocol request and UDP datagrams of `ports`, and `azhaq fuzz`, which sends the method and body you give it with your wordlist's words in them. Chrome sends GET, HEAD and OPTIONS only: the writes a page's scripts would send are mapped and listed, not sent. Operations read from an API description or a script call are mapped with their method and fields; only the parameterless GETs among them are asked.
- **Every outcome said.** Each command ends with a summary: what failed and whether it is worth retrying, targets that never answered, what was left alone and why, the limit that stopped the work. The exit code says the same (0 complete, 3 finished with failures, 4 stopped by a limit), so a script or an assistant never has to guess whether an empty result is an honest zero.

## Limitations

- Requests to a target are limited by concurrency per host (4 by default) and an optional delay; path guessing, parameter discovery and port scans also have a rate. Third-party sources and DNS resolvers have rate limits.
- Organization seeds rarely expand, because public RDAP has no search by organization name.
- Routes built at run time from anything but constants, template literals and variables assigned once (user input, server responses, functions of several variables) are seen only with `-browser`, and only those a page requests while it loads: Azhaq does not click.
- Routes only the server knows (admin APIs no page mentions) are found only by the path sweep or an API description.
- One SQLite file holds a run, written by the run's own process; workers send their results to it rather than writing a shared store.
