# What Azhaq prints

Every command follows the same contract, so a script or an assistant can read any of them the same way.

- **stdout** carries results only: one per line, or one JSON object per line with `-json`.
- **stderr** carries progress, failures as they happen (the first three of each kind), and a **summary** at the end. With `-json` every stderr line is JSON and the summary is one object with `"type":"summary"`. With `-silent` the summary is printed only when something failed or was cut short (a source or archive that failed counts, though the exit code stays 0). A takeover candidate is a finding, not a note, so `-silent` prints one line for each on stderr, `[takeover] shop.example.org -> gone.azurewebsites.net (Azure, dangling)`, and stdout stays one result per line. A command that is still working after 10 seconds says so every 10 seconds, so a run paced at a request a second is not taken for a hung one: `azhaq: 1m30s, 62 requests sent (1/s), 38 tasks left; -max-requests 80 ends it in about 18 s` (the pace is that of the last interval, the tasks are those known so far, and the end is the sooner of the request cap and `-timeout`), or with `-json` the object `{"type":"progress","seconds":90,"requests":62,"requests_per_second":1,"tasks_done":70,"tasks_left":38,"ends_by":"-max-requests 80","ends_in_seconds":18}`. A run paced slowly says so as it starts (`-rate 1 paces requests to 1/s: the cap of 80 requests …`). `-quiet` and `-silent` print neither, and a run that ends within 10 seconds prints no progress line. Nothing of this goes to stdout.
- The **exit code** says whether the work is complete.

`azhaq help -json` lists every command and flag with its type and default.

## Exit codes

| Code | Meaning | What to do |
| --- | --- | --- |
| 0 | Complete. | Use the results. |
| 1 | Error: the command could not do its job (a database it cannot open, Chrome missing for `-browser`). | Read the message. |
| 2 | Usage: bad flags or input, such as targets that are all outside the scope given (`every target is outside the scope (2 left out): 127.0.0.2, 127.0.0.3`: the message names them; a range no allow rule touches counts, and `ports` and `dns` say it too). Nothing was sent. | `azhaq help COMMAND`; for a scope refusal, the target or `-allow`/`-scope`. |
| 3 | Finished, but some sources or requests failed. The results are usable. | The summary lists each failure, whether it is worth retrying, and its targets. |
| 4 | Stopped by a limit (`-max-requests`, `-timeout`, `-daily-requests`, `-max-items`), by the kill file (`-kill-file`, default `DB.stop`) or by a signal (Ctrl-C, `kill`, SIGHUP: SIGINT, SIGTERM and SIGHUP all stop a command the same way, with its summary and its ledger sealed) with work left. | `azhaq resume -db FILE` continues where it stopped; with a kill file, remove it first. |

`watch` exits with the code of its run (one run, without `-every`). `ledger -verify` exits 3 when the chain is broken or lines follow the last seal.

A run keeps the answers it got in its workspace until nothing is left to resume, so `azhaq resume` does not ask again what the run already asked: the requests of a run stopped and resumed add up to a few more than those of one uninterrupted run, not twice as many. A port scan the budget cut short scans that address again. A drop-in (`subs`, `probe`, `dirs`, …) run without `-db` uses a temporary database and cannot be resumed; `run` without `-db` writes `azhaq-TIME-PID.db` in the current directory (or `$AZHAQ_DB`).

Failures on fan-out are listed with `"fanout": true` and do not make the exit code 3: the map of what you asked about is still complete. Fan-out is what you did not ask about: a name found on the way, and the third-party lookups (subdomain sources, archives, RDAP) of a domain that is only the domain of a URL you mapped. Ask for the domain itself (`-domain`, `subs -d`, `urls -d`) and their failures count, except a source that failed while other sources answered for the same domain: it is listed with `"partial": true` and does not make the exit code 3 (sources fail all the time; an exit code that is always 3 says nothing). crt.sh is one of these: it holds the most names of any certificate log, but it is also the flakiest (gateway 5xx are common), and a run that got its names from the other sources should not fail a CI gate over a transient crt.sh blip — the failure is still listed. `-fail-on-errors` counts every failure, crt.sh's among them. A name answered SERVFAIL on every attempt, by two resolvers or more, on two passes, is not a failure: the resolvers answered alike, and the name's own DNS is broken (a lame delegation) for everyone; it is dead, with `result` `servfail`. Resolvers that time out or answer REFUSED (refusing this machine), or SERVFAIL from one resolver alone, are a failure. One resolver's NXDOMAIN, or an answer without an address (`nodata`, a CNAME chain that ends without one), is not a name dead either: a second resolver is asked once (another operator's, with the default pool: 1.1.1.1 is checked with 8.8.4.4, not 1.0.0.1), and the name is dead only when both agree; a public resolver answers NODATA now and then for a name every other one resolves. Names under a wildcard zone and special-use names are not asked twice.

## The summary

```json
{"type":"summary","command":"run","version":"0.6.0","complete":false,"exit":3,
 "results":148,"counts":{"URLs":123,"api":33,"auth":12},"seconds":7.4,"requests":195,
 "db":"app.db","run_id":"…",
 "unreachable":["http://testphp.vulnweb.com/"],
 "failed":[{"collector":"azhaq-http","error":"timeout","retryable":true,"count":34,
            "targets":["http://testphp.vulnweb.com/login.php","…"]}],
 "skipped":[{"target":"engage.tesla.com","reason":"outside the scope"}],
 "stopped":"the request budget of 500 is spent, 41 tasks known and not done (the cap holds for each run: azhaq resume sends up to 500 more, or as many as its -max-requests says, 0 for no cap)","resume":"azhaq resume -db app.db",
 "notes":["…"],"next":["azhaq query -db app.db -type Hostname"]}
```

| Field | Meaning |
| --- | --- |
| `complete`, `exit` | As in the table above. |
| `results` | What the command printed on stdout: names, web services, map rows. |
| `counts` | A breakdown of the results, per command. |
| `requests` | Requests sent to targets, port connects included (not those to third-party sources). |
| `db` | The database the results are in (absent when it was temporary). |
| `unreachable` | Targets you gave that never answered. |
| `takeover` | Names another party may take over, each with `host`, `service`, `target` (the CNAME target), `evidence` and `strength`. `strong`: the name's CNAME points at a hosting service whose own page says nobody claimed the name (GitHub Pages' "There isn't a GitHub Pages site here.", S3's `NoSuchBucket`, Heroku's no-such-app page, Pantheon, Ghost, WordPress.com, Help Scout, ReadMe, ngrok, Bitbucket, Surge), or at a name whose ICANN domain is not registered (a cloud's shared suffix such as `elb.amazonaws.com` is no registry and never counts). `dangling`: the CNAME points at a web name on Azure (App Service, Cloud Services, CDN, API Management, Container Instances, HDInsight, Blob Storage), Elastic Beanstalk or Fly.io that does not resolve. `page`: one of those services' own pages with no CNAME known; where DNS shows the name points elsewhere, nothing is said. Read from DNS answers (`subs -live`, `dns`, `run`) and front pages (`probe`, `run`); confirm by hand before reporting. The text summary prints each as `! takeover candidate`; with `-silent` and nothing else to report, each is printed alone as `[takeover] name -> target (service, strength)` on stderr. `dns` and `subs -live` rows carry the same object as `takeover`. |
| `failed` | Work that did not get its answer, grouped by collector, source and error, most frequent first. `retryable` is true for timeouts, dropped connections, 429 and 5xx. `source` names a third-party source (crtsh, wayback). `targets` names up to 100; `azhaq query -db FILE -failed` lists every failed target, the list to retry. |
| `skipped` | Targets and requests Azhaq chose not to touch, with the reason: outside the scope, would end the session, a scope entry a run cannot use. Chrome's requests outside the scope are refused before they leave and listed here without their query string, `outside the scope (Chrome)` (`outside the site (Chrome)` without a scope: the registrable domain or address of the pages it was pointed at), the first 100 URLs of a run; `notes` gives the number of requests when there were more. Chrome sends GET, HEAD and OPTIONS only (outside signing in): a write a page or its scripts would send (a POST, PUT, PATCH or DELETE, a beacon, a form a script posts) is refused before it leaves and listed as `a page's script would send a write`, by method and URL without its query (`POST http://127.0.0.1:3001/api/track`); its route is mapped with that method (`ops` with `source` `browser`). With `-browser-writes` pages send their writes, which change data on the target, and nothing is listed. Chrome saves nothing to disk: a download (a URL that is a file, an `<a download>`, a `Content-Disposition: attachment` answer) is refused for the whole browser and listed as `Chrome would download it`, by URL without its query and the name Chrome would have given the file (`http://127.0.0.1:3001/ftp/incident-support.kdbx (incident-support.kdbx)`); the request itself was sent and counted, only what it answered is dropped. |
| `junk` | `urls`: how many URLs on the domains were left out as junk, by reason (`"scanner payload": 3`, `"scanner probe"`, `"directory listing sort link"`, `"script placeholder (NaN, undefined, null)"`, `"dot segment"`, `"malformed link (wildcard, quote, bracket, ellipsis)"`, `"link cut at the end of its sentence"`), each URL once; `counts` has the total as `dropped as junk`, and a note says it (`7 URLs dropped as junk (…; -raw keeps them)`). `-raw` prints them and drops none. |
| `sources` | `subs` and `urls`: how many sources (for `urls`, archives) answered, which failed and why, and what each gave. `asked`, `answered`, `failed` (sources in the default set or named with `-sources`) and `off_by_default_failed` (ran only because of `-all-sources`) count each source once for each domain, as `counts` does, so `asked` is `answered` plus `failed` plus `off_by_default_failed`; a source skipped for want of a key is not asked. `names` (`urls` has `urls` instead) is what each source gave, before any DNS check or filter. `seconds` is how long each source took (the longest over the domains): the largest one set the run's time, and a note names it when it held the run (`crtsh took 60 s, the next slowest source 3 s, so it held the run`). `failed_sources` has each failed source's reason (`"wayback": "web.archive.org answered 429"`; with several domains each reason starts with its domain). The text summary ends with the same, and says why the exit code is what it is: `23 of 33 sources answered, 10 failed (listed above); exit 0 because other sources answered for the same domain (-fail-on-errors makes it 3)`. `dns` asks resolvers, not sources, and has no such block. |
| `partial` (in `failed`) | A third-party source failed while other sources answered for the same target. |
| `degraded` | `subs` only: true when `sources failed` (below) is above 0, so a source the run relies on did not answer and the names may be incomplete. The text summary says it on its first line (`DEGRADED: 7 of 38 sources failed`). It does not change the exit code: a failure the other sources made up for is listed as `partial` and the exit stays 0 (3 with `-fail-on-errors`). Failures of sources that ran only because of `-all-sources` never set it on their own. |
| `stopped`, `resume` | The limit that stopped the work and the command that continues it. |
| `notes` | Caps that were hit and other things worth knowing that are not failures: `ledger: 148 requests and connections recorded in app.db.ledger.jsonl (azhaq ledger -verify app.db.ledger.jsonl)`; `path checks: 28 skipped (an API description was already found)`; `screenshot of URL not taken: the page needs about 26 requests and 8 were left (raise -max-requests)` (or `the budget was spent before the page loaded`); `GraphQL URL: introspection disabled: schema recovered (partial)` or `introspection: full schema`; for `subs`, the `coverage` line below. |
| `next` | Commands worth running next. A run without `-browser` whose target pages leave their links to their scripts (three or more `{{templates}}` in the text; or Markdown in the text, whose links are read as text, or an empty shell of a front page, with fewer than 10 routes found on its origin) gets `azhaq run -url ORIGIN/ -browser …` with the page that showed it: `(/learn/vulnerability/a1_injection and 11 more pages: Markdown its scripts turn into links; read as text here, Chrome sees the page as rendered)`. A run that found a GraphQL endpoint and did not read its schema (no `-graphql`, or its host outside the scope) gets `azhaq run -url ORIGIN/ -graphql -allow HOST …   (/graphql and /graphiql answer like GraphQL; -graphql reads the schema by introspection)`. A run without a session (`-login`, `-cookie`, `-header`) whose target site shows a sign-in form (a form that takes a password) gets `azhaq run -url ORIGIN/ -login PAGE -login-user USER -login-pass PASS -allow HOST …`. |

## run

The map, one row per entity, best first: the target's own pages and APIs, then what it led to. `-json` prints one object per row:

```json
{"type":"URL","key":"http://127.0.0.1:3001/api/Users","scope":"target","coverage":"visited","role":"auth",
 "status":401,"title":"UnauthorizedError: No Authorization header was found","methods":["GET","POST"],
 "params":["email","password"],"proof":"status=401 …","first_seen":"2026-10-26T14:23:40Z"}
{"type":"URL","key":"http://127.0.0.1:3001/rest/2fa/verify","scope":"target","coverage":"hint","role":"api",
 "methods":["POST"],"body":["tmpToken","totpToken"],"ops":[{"method":"POST","body":["tmpToken","totpToken"],"source":"js-call"}],
 "found_in":[{"script":"http://127.0.0.1:3001/main.js","line":6472,"col":88,
              "snippet":"this.http.post(`${F$.hostServer}/rest/2fa/verify`,{tmpToken:localStorage.getItem(`totp_tmp_token`),totpToken:t})"}]}
{"type":"URL","key":"http://127.0.0.1:3001/#/administration","scope":"target","coverage":"hint","role":"client-route",
 "guard":"canActivate","proof":"guard=canActivate","found_in":[{"script":"http://127.0.0.1:3001/main.js","line":6622,"col":727,
 "snippet":"…AboutComponent});var pN=[{path:`administration`,component:Su,canActivate:[cs]},{path:`accounting`,"}]}
{"type":"URL","key":"ws://127.0.0.1:3001/socket.io","scope":"target","coverage":"hint","role":"websocket","protocol":"socket.io"}
```

| Field | Values |
| --- | --- |
| `type` | `URL`, `Hostname`, `Domain`, `IPAddress`, `Organization`, … |
| `scope` | `target`: what you asked about. `fanout`: found on the way (other hosts, CNAME targets). |
| `coverage` (URLs) | `visited`: fetched and answered as a page of its own. `catchall`: answered with the page every unknown path gets (a single-page app's shell). `error`: requested, no answer. `gone`: answered 404 or 410 (found in an archive or a link, not there now). `hint`: found (in a script, an API description, an archive) but not requested (an archive's static assets, images, fonts and the like, are never requested, whatever hides their extension), or called by scripts only with POST or PUT, or written to only by a page in Chrome (a GET that answers 404, 405 or the catch-all page says nothing about such a route), or named only in scripts with no GET call among them while a GET answers 404 (`proof` says `GET answers 404; found only in scripts, method unknown`). `skipped`: found (by a link, a script's call, an API description or an archive), not requested because its name says a GET would change something; `word` names the verb, and the summary lists it under `skipped` (`left alone`). This is the map's rule: a wordlist sweep (`dirs`, `-dirs`, `fuzz`) asks every word, `/logout` included, as ffuf does, and holds words back only under a session (see `dirs`). `capped`: left when a limit was hit, or when its origin stopped answering (5 connects or timeouts in a row with no answer between them: the rest of that origin's work is left for `azhaq resume`, listed under `left alone` with `ORIGIN stopped answering after 5 timeouts`, and `stopped` names the origin). A version prefix alone that only a script's strings name (`/v3`) is left out of the map when it answers 404 or the catch-all page. |
| `evidence` (URLs) | How azhaq knows the row, the strongest level any of its sources reaches: `answered` (azhaq sent the request; `status` and the rest are what came back), `browser` (Chrome sent it while loading the page), `described` (an API description lists it, not asked), `called` (a script calls it, not asked), `linked` (a page, a form or a script string names it, not asked), `archived`, `guessed` or `given` (you named it and nothing else holds it) ([CONCEPTS.md](CONCEPTS.md#evidence-how-azhaq-knows-a-url) defines them). A row folded into a template takes the strongest level of its instances. `evidence_from` lists the collectors behind it, sorted. Only URL rows have a level; `coverage` says what was done (`skipped`: deliberately not asked). |
| `answer` (URLs) | Set when the status says less than it looks: `500 without input` is a 5xx that azhaq's plain request got from a route that takes names (query or body) and was sent none of them. |
| `role` (URLs) | `app` (a front page), `auth` (401), `forbidden` (403), `api`, `page`, `script`, `asset`, `sourcemap`, `manifest` (a bundler's build manifest: Vite's `.vite/manifest.json`, Create React App's `asset-manifest.json`, Angular's `ngsw.json`, Nuxt's build meta), `client-route` and `websocket` (below). |
| `client-route` | A view a single-page app's router draws, read from its route table (Angular's `RouterModule`, React Router's `<Route>` and `createBrowserRouter`, Vue Router): `http://host/#/administration` for an app that routes by the hash, else its path (`http://host/admin`), parameters as `{name}`, nested routes joined to their parents'. A view after the hash is never requested: the server answers every one with the app's shell. A view in the path is asked for once with a GET, as the server may answer it itself: a sign-in's 401 makes the row `auth`, a page the server renders `page`, with the guard still on the row and in its `proof`; a view the shell answers stays `client-route` (`catchall`), a template (`/reports/{id}`) is not requested. `guard` is what the router checks before it draws the view, a parent's guard holding for its children: Angular's `canActivate`, `canMatch`, `canLoad` or `canActivateChild` (with the guard's name when the build keeps it, `canLoad AdminGuard`), Vue's `meta.requiresAuth` (or another meta key about sessions or roles) or `beforeEnter`, a React wrapper such as `RequireAuth` or `PrivateRoute`. A string in a script that names a view (a router link, `router.navigate(['/order-completion', id])`) is that view's, listed in its `found_in`, not a page of its own. With `-browser`, Chrome does not open the views. |
| `websocket` | A WebSocket endpoint a script opens (`new WebSocket(…)`, `SockJS`, a `ws://` or `wss://` URL, a socket.io client's `io(url, {path})`), as `ws://` or `wss://` (the page's scheme when the script builds the URL from `location.host`). Never requested. `protocol` is `socket.io` for a socket.io endpoint, whose `namespace` (`/chat`) is given when the app's call names one; the library's default path, `/socket.io`, stands when the app's call cannot be read. Third parties' sockets (chat widgets, analytics) are left out. |
| `role` (names) | `live` (resolves; a host you gave, or a name under a domain you gave), `sibling` (resolves; found on the way, under another domain), `unresolved` (from a source or a list, not looked up), `dead`, `wildcard`. |
| `ops` | each operation on the route: `method`, `query`, `path`, `header`, `body` (field names), `body_type`, `auth` (the description asks for credentials), `summary`, `operation_id`, `source` (`js-call`, `openapi`, `graphql`; `browser`: a write a page in Chrome sent or was refused, with the names its query and body carried, never their values). |
| `body` | the body field names of all its operations, whatever described them: a script's call, an API description (served or found), a GraphQL schema (argument names), a request taken in from katana. |
| `status`, `title` | The URL's own answer (the first hop of a redirect). Without a scope, a redirect is followed only within the site (same registrable domain or address); with one, only inside it. Chrome is held to the same rule for everything a page asks for. |
| `methods`, `params` | From API descriptions and call sites in scripts; `params` also holds the names in the URL's own query string. The query names of the links on a page are on the links' rows, not the page's. |
| `forms` | `{"method","action","enctype","fields","files"}` for each form on the page. A form whose action is empty or `#` submits to the page itself: `action` is the page's URL with its query. `enctype` is a POST form's encoding (`application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`), `files` the fields that are file inputs. |
| `found_in` | Where scripts name the route, up to three places, calls first (for a route on another host than the page whose script named it, the script on that host, which is also what links to it in `show`): `script` (its URL; the page's for a script inside the page, with `inline` true and the page's line numbers), `line` and `col` (bytes, from 1), `snippet` (up to 120 bytes: the call as written, or the string with the code around it; credentials in it, such as JSON Web Tokens, bearer tokens, secrets set to a literal or in a query string and long keys, read `[redacted]`), and `source`, the original file, when the route was read from a source map's sources (`line` and `col` are then that file's). |
| `watch` | Parameter and body names worth trying first, by what their name says they take: `returnUrl (redirect)`, `url (url)`, `file (file)`, `cmd (command)`, `isAdmin (debug)`, `userId (id)`, `callback (callback)`. The text map prints them on a `watch:` line under the row. |
| `template`, `count` | Pages that differ only by an ID are folded: `/product?id={n}` with the number of URLs folded. A query value that names a page (`index.jsp?content=about.htm`, `view=grid`) is not an ID: each is a page of its own. Three URLs of a template are requested (`-per-template N` changes it). |

A GraphQL endpoint whose schema was read with `-graphql` has one op per query, mutation and subscription: `method` `POST`, `summary` its signature (`mutation login(username: String, password: String): Login`), `operation_id` the field name, `body` the argument names, `source` `graphql`.

A run's summary counts `client routes` and `websockets` apart from `URLs`. The text map lists them after the routes of the server with the same rank, with `guard=…`, `protocol=…` and `namespace=…` as their proof.

`azhaq query -fields key,evidence,evidence_from` shows the level, and `azhaq query -evidence answered,described` keeps the rows with those levels. The text map ends a row that is not `answered` with `[browser]`, `[described]`, `[called]`, `[linked]`, `[archived]`, `[guessed]` or `[given]`, and writes `500 without input` after the proof of a row that has an `answer`.

A string in a script that is only the start of a path, `"/rest/user/" + id` or a base such as `this.hostServer + "/rest/web3"` that calls are built on (`/rest/web3/submitKey`), is not a route: it has no row, is never requested, and is kept as a rejected string with the reason `the start of a path a script joins more to` (`crawl -rejected` lists it). A string with a query (`"/search?q=" + q`) names its route and stays. `export -format jsonl` carries `evidence` and `evidence_from` on each entity line, `export -format openapi` `x-azhaq-evidence` on each operation, and `export -format html` an Evidence column in the API and map tables.

The text map prints the same rows, one per line, with forms and parameters indented below, and a GraphQL endpoint's operations by their signatures (the first 50; the rest are in `-json` and the exports). `azhaq show URL` prints where scripts name it under `found in`, one place per line as `script:line:col  snippet`:

```
found in
  http://127.0.0.1:3001/main.js:6472:88  this.http.post(`${F$.hostServer}/rest/2fa/verify`,{tmpToken:localStorage.getItem(`totp_tmp_token`),totpToken:t})
```

## Drop-in commands

Their `-json` output uses the field names of the tool they stand in for, so existing `jq` filters keep working.

| Command | Fields |
| --- | --- |
| `subs` | `host`, `input` (the domain), `source` (the first source that gave the name), `sources` (all of them; `dns-brute` or `permute` for a name found by `-w` or `-permute`; `history` for a name an earlier run kept, below; `cname` for a live name DNS met as another name's CNAME target); `unverified: true` on a name only subdomain.center guessed or the name history held, which no DNS lookup checked (without `-live`; below); `wildcard_certificate: true` on a name a certificate gave as `*.name`; with `-live`, dnsx's `a` and `aaaa` (the addresses; a name that is only a CNAME has none), `cname` (the chain) and `cdn` (the CDN or WAF in front), and with `-oI` an `ip`. A name that is a takeover candidate has `takeover` (`service`, `target`, `evidence`, `strength`) on its row (with `-live`: the candidates are found by DNS), and every candidate is in the summary (`takeover`). With `-cs` the text form is `host,[source,source]`, with `-live -oI` `host,ip,source`; `-oD DIR` also writes `DIR/DOMAIN.txt` (`.json` with `-json`) for each domain. |
| `dns` | dnsx's fields, in its order, each left out when empty: `host`, `ttl` (of the first record that has one), `resolver` (the resolvers that answered), `a`, `aaaa`, `cname` (targets, no final dot), `mx`, `ptr`, `soa` (`name`, `ns`, `mailbox`, `serial`, `refresh`, `retry`, `expire`, `minttl`), `ns`, `txt` (the strings of a record joined), `srv` (targets), `caa` (values), `all` (every record as text; `-omit-raw` drops it), `raw` (with `-raw`), `has_internal_ips` and `internal_ips` (an answer in a private, loopback, link-local, documentation or multicast range), `status_code` (`NOERROR`, `NXDOMAIN`, `SERVFAIL`, `REFUSED`, ...) and `status_code_raw` (the number, left out for 0), `takeover` (not a dnsx field: the finding of a name whose CNAME points at what is gone), `trace` and `axfr` (`{host, chain: [rows]}`, with `-trace` and `-axfr`), `timestamp`, `hosts_file` (with `-hf`), and with `-cdn` `cdn` (true for a CDN), `cdn-name` and `cdn-type`, with `-asn` `asn` (`as-number`, `as-name`, `as-country`, `as-range`), and `query-time`. `-json` gives a row for every name a resolver answered, one that does not exist too (`status_code` `NXDOMAIN`, no records); with a type flag (`-a`, `-mx`, ...) only the names that have a record of that type, or with `-rcode` the names whose answer has that code. `subs` ends with a note such as

```
coverage: the independent sources hold about 1609 names; this run has 1400 of them (87%) — an estimate of what the sources know, not of every name that exists; the other 47 of the 1447 names came from the name history, from guesses checked in DNS or as CNAME targets, which the estimate leaves out
```

It is a Chao1 estimate over how many independent sources gave each name: S + f1²/(2·f2), with f1 names given by one source and f2 by two (with f2 = 0: S + f1(f1−1)/2). Independent means every source except the ones that pad their answer (subdomain.center) and `history`; a name only those gave is in the output but not in the count. It needs two independent sources that gave names, and counts the names printed (with `-live`, the live ones). It estimates what the sources know, not every name that exists. The `azhaq-subdomains` payload has `"coverage": {"observed", "estimated", "share"}`; the row of a sampled source (subdomain.center) in `sources` has `"population_estimate"`, a Schnabel estimate of how many names one call draws from, when its rounds repeated names.

### ports: targets, formats and limits

Targets are a name, an address, `host:port`, a URL, a CIDR range or an AS number (`AS13335`: the prefixes RIPEstat lists, said in the summary), comma-separated in `-host`, one per line in `-l` or on stdin, or as arguments. A `host:port` is asked that port only, unless `-p`, `-tp` or `-pf` is given, which then apply to every target. A range is split into blocks of 256 addresses that the run takes one at a time and records, so it has no size limit and `azhaq resume` continues it; an IPv6 range larger than /104 is refused, since no scan finishes it. A name costs the DNS queries of its A and AAAA records and no others. An address that shows nothing has no row; the summary's `counts` has `addresses`, and its notes say how many addresses were not up (`-wn`), were outside the scope, or had ports that neither accepted nor refused a connect.

| Flag | Output |
| --- | --- |
| (none) | `host:port`; a UDP port is `host:port/udp` |
| `-json`, `-j` | one object per open port: `host`, `ip`, `port`, `protocol`, `tls`, `cdn`, `cdn-name`, `timestamp` (UTC, RFC 3339), `service`, `product`, `version`, `title`, `banner`, `subject_cn`, `subject_an`, and `state` for UDP |
| `-csv` | a header line, then the same fields as columns (`-lof` lists them); a list is joined with spaces |
| `-eof a,b` | leaves fields out of `-json`, `-csv` and `-oA`'s JSON |
| `-oX FILE`, `-oG FILE` | nmap XML and nmap greppable output (`-` for stdout); hosts in address order, ports by number, `service` without the `?` that marks a guess from the port number alone (`method="table"` in the XML) |
| `-oA BASE` | `BASE.json`, `BASE.xml`, `BASE.gnmap` |
| `-sn` | the addresses that are up, one per line (`-json`: `{"host","ip","up":true,"timestamp"}`) |

The XML and greppable layouts follow naabu's. `-timeout` is how long the run may take (`90s`; `ports -timeout 500` is refused with a pointer to `-connect-timeout`).

How the scan runs, and what it does not do silently:

- A CDN or WAF address is asked ports 80, 443, 8080 and 8443 only, because its other ports are the provider's other customers'. The row has `cdn` and a `note`, and the summary names the addresses. `-cdn-full` scans them in full.
- A port that neither accepts nor refuses is asked again, after the others: once when few did not answer (the default), or `-retries N` more times, `-retries 0` never. When a connect timed out, the pass waits one connect timeout (at most 3 s) first: a listener whose accept queue is full makes Linux drop the SYN, and the port is open once its service has drained the queue. Each ask counts against `-max-requests` and is in the ledger. A port still silent is in the row's `filtered_ports` and in the summary.
- `-pts N` stops asking a host after N open ports (a host that answers every port); the row has `"threshold":true` and the summary names the host (ports already in flight are still asked, so a few more than N may be listed).
- `-detect none` connects and closes (one connect per port, as naabu without `-sV`), `-detect banner` reads what the service says on that connection, `-detect all` (default) also asks a silent port for HTTP and TLS, then one request of each protocol that waits to be asked, each on a connection of its own (at most 24 connects after the first). Every connect, whatever its purpose, counts against `-max-requests`, takes a token of the pace and is in the ledger.
- `-proxy host:port` (SOCKS5) and `-source-ip` make the TCP connects go through that proxy or from that address; the service probes beyond the first connection dial on their own, so with either the scan asks the banner only, and the summary says so. UDP is not sent through a proxy (`-proxy` with `-udp` is refused).
- With `-wn` or `-sn`, an address is up when a connect to 80 or 443 is accepted or refused, asked twice; a host that drops both is called down, and the summary counts them.

### ports: UDP, products and versions

`ports -udp` asks UDP ports too: the 25 common ones (`-pu top`: 53, 67, 69, 111, 123, 137, 161, 500, 514, 520, 623, 1194, 1434, 1900, 3478, 4500, 5060, 5351, 5353, 5683, 10001, 11211, 27015, 47808, 51820), or the list `-pu` gives (`-pu 1-1024`, `-pu top,5354`: list names and numbers combine, in `-p` too); `-p none` leaves the TCP ports out. In `run` it is `-ports-udp SPEC` (`top`, `full` or a list). A port with no known protocol is asked a DNS query, then an SNMP get with community `public`, then memcached's version, then an empty datagram, until one answers. No privileges are needed: each port gets one datagram on a connected socket, and the kernel tells an ICMP port unreachable from silence.

| What came back | State |
| --- | --- |
| a datagram | `open`, with the service, product, version and banner the reply gives |
| an ICMP port unreachable | `closed` |
| nothing, every way asked | `open|filtered`: a service that ignores the request, or a filter |

The request is the harmless one of the protocol the port usually carries: DNS `. NS`, an NTP client request, an SNMP GET of `sysDescr.0` (community `public`), SSDP M-SEARCH, an mDNS service query, a NetBIOS node status request, an IKEv2 header, a STUN binding request, memcached `version`, BACnet Who-Is, CoAP `GET /.well-known/core`, a TFTP read of a file that does not exist (an ERROR packet proves TFTP; it is read on a socket that is not connected, since the server answers from a port of its own), the portmapper's DUMP (the programs it lists), the SQL Server Browser's CLNT_UCAST_EX (version), a SIP OPTIONS, NAT-PMP's public address request, Ubiquiti's discovery request, an ASF presence ping and, as the second ask of 161, an SNMPv3 engine id discovery (the vendor is read from the engine id); a port with no known protocol gets the generic ones. A sysDescr that names Linux, Cisco IOS, JUNOS or Windows gives `product` and `version`. Nothing logs in, guesses a credential or changes state. Every datagram counts against `-max-requests`, is paced by `-rate` and goes in the request ledger as kind `udp`. A CDN or WAF address is not asked.

JSON rows have `"protocol":"udp"` and `"state"`. In a workspace, the `ports` row has `udp_open`, `udp_open_filtered`, `udp_closed`, `udp_scanned`, `udp_limited` and `udp_services` (port, state, service, product, version, banner). Plain output lists `host:port/udp` for an open port and `host:port/udp open|filtered` for a silent one (the first field is the same, `-silent` prints the same lines); `-json` and `-csv` rows have `"state":"open|filtered"`, and each is a result, counted in `results`. The summary says what the state means (`1 UDP port open|filtered: no reply and no ICMP port unreachable after every request its protocol has (a silent service or a firewall); …`). An address asked on its own, or a name, lists every silent port up to 64; past that the rows would be noise, so the summary counts them and the workspace row's `udp_open_filtered` keeps them (`udp_unlisted` is how many). In a range, an address that answered nothing at all on UDP (down, or dropping it) has no rows: the range row counts its `udp_silent_ports` and `udp_silent_addresses` and the summary says so; ask the address on its own to list them. An address that refused or answered some port, or has an open one, lists its silent ports. On a loopback or LAN address, `open|filtered` usually means a service that does not answer a request it does not understand; a closed port there answers with an ICMP error and is reported `closed`. Across a firewall that drops ICMP, closed ports also read `open|filtered`. A host that refuses with ICMP but rate-limits it (Linux sends about one a second) leaves closed ports silent too: when some ports were refused and at most 80 silent ones remain, those are asked again one at a time at that pace so each reply can arrive (slower, on a non-loopback address only); when more remain, they stay `open|filtered`, `udp_limited` counts them and the summary says some may be closed. A port is `closed` only on an ICMP unreachable for that port.

## roles

One row per endpoint whose answer depends on the session (`-all`: every endpoint compared), and with `-replay-writes`, one per write asked (its `method` set):

```json
{"url":"http://localhost:5000/books/v1/aliceBook","verdict":"reads another role's object",
 "template":"http://localhost:5000/books/v1/{book_title}","found_by":["alice"],"owner":"alice",
 "owner_by":"item of /books/v1: user alice names alice (sub claim of alice's token); the answer's owner alice names alice (sub claim of alice's token)",
 "readers":["bob"],"sensitive":["secret"],"status":{"anon":401,"alice":200,"bob":200},
 "confidence":"proved",
 "evidence":"bob got alice's answer (the same body, 79 bytes); item of /books/v1: user alice names alice; the answer's owner alice names alice; a made-up qmxreHtgf got bob 404; both ways: alice reads bob's too",
 "control":{"url":"http://localhost:5000/books/v1/qmxreHtgf","value":"qmxreHtgf","answers":{"bob":{"status":404,…}}},"both_ways":true,
 "answers":{"anon":{"status":401,"length":95,"hash":"…","error":true},
            "alice":{"status":200,"length":79,"hash":"9f…","keys":["book_title","owner","secret"],"sensitive":["secret"]},"bob":{…}}}
```

| Field | Meaning |
| --- | --- |
| `status` | Each role's status; 0 for a role that was never asked. |
| `dir` | The `-dir` of the run, as an absolute path: `roles show`, `report` and `hunt` find the answers behind the row there. |
| `answers` | Each role's answer: `status`, `length`, `hash` of the body, `keys` (a JSON answer's field paths, nested: `data.user.email`, `data[].id`), `error` (a JSON answer shaped like an error, such as `{"status":"error"}`), `refusal` (a 2xx answer that is its origin's refusal page, or that `-refusal` matches; see below), `sensitive` (its fields that hold passwords, secrets, keys, tokens, card numbers), `location` (where a redirect sends the role), `session_suspect` (see below). Every answer is compared by its body: one the run kept without it (a URL the `-paths` list found keeps its status only) is asked again, with the role's session. |
| `found_by` | The roles whose own runs reached the URL, or, for an object URL, whose answers held its identifier. |
| `template` | The route an object URL fills: its path parameters filled with identifiers the roles' answers held, or given with `-id`. |
| `owner` | The role whose own object it is: given with `-id ROLE:…`; known from who the role is (see below); or an identifier only that role's answers held (in the route's own list, such as `/api/Addresss` for `/api/Addresss/{id}`, while the same list read by another role did not; or in a field named after the parameter, and nowhere in the other roles' answers). What the object's own answer says of its owner confirms, names or undoes it, as far as what filled the route allows (see below). |
| `owner_by` | What says the object is the owner's, to check in one look: `bid claim of alice's token → /rest/basket/{id}` (an identifier the role's session holds, where it was read, and the route it fills), `authentication.bid in alice's login answer → /rest/basket/{id}`, `item of /books/v1: user alice names alice (sub claim of alice's token)` (a list item whose own fields name the role), `in alice's /api/Addresss and not the other roles'`, `in alice's answers alone`, `given with -id alice:book_title=My book`, and, after `; `, what the object's answer says: `the answer's UserId 27 names alice (data.id claim of alice's token)`, `the answer's BasketId 8 is alice's basket (bid claim of alice's token)`. For a write, where the write came from (`alice.har`, `PUT /api/BasketItems/{id} with an empty body`). |
| `confidence` | On a row where a role reads or writes another role's object: how surely the object is the owner's. `proved`: what filled the route named the owner from its session (an identifier the session holds by its full name, a list item that names the role by it), its own list, or `-id`, and the object's own answer confirms it. `likely`: one of the two (a short name such as `bid` the answer bears out; an owner the answer alone names; `-id` the answer does not speak to). `guess`: an identifier only the owner's answers held and nothing more, or a route that answers any identifier. A proven cross write is always `proved`: the owner's object is shown to have changed. |
| `evidence` | On the same rows, why in one line: who got what the owner got (`bob got alice's answer (the same body, 155 bytes)`, or `the same fields around 8`), `owner_by` without the routes and where each value was read, what a made-up identifier got (`a made-up 1000022 got bob 404`), and `both ways: alice reads bob's too`. For a write: who was let, as the owner was, and where the write came from (`bob got 200:80, as alice did (200:80); PUT /api/BasketItems/{id} with an empty body`). The text table prints `confidence` and `evidence` after the route. |
| `control` | On a row where a role reads another role's object: what its readers got for a made-up identifier on the same route (`url`, `value`, each reader's `answers`, and `alike`: the readers it answered as a real object). |
| `both_ways` | The owner reads one of its reader's objects on the same route too; a note says it once per route and pair (`alice and bob read each other's objects on /rest/basket/{id}`). |
| `session_suspect` | An answer of the row was asked after its role's session last proved alive, and the session did not prove alive after it (see canaries below). The text table marks the answer with `?` and the row with `· session suspect: bob`. |
| `readers` | For the verdicts that say who reads it: those roles. |
| `sensitive` | For the verdicts about sensitive fields, and on object rows: the fields. |

A role reads an endpoint when it gets a 2xx answer that is not an error. A refusal is any 4xx, an error answered with a 2xx status, a 2xx page that is its origin's refusal (`200 Access denied`, see below), a redirect to a sign-in page (a path such as `/login`, `/users/sign_in`, `/auth/…`, another site's sign-in service, or the `-login` page), and a redirect to the site's front page while another role reads the endpoint: on a cookie-session app, the visitor sent to `/login` makes a page `signed-in only`. Verdicts, worst first, as `-json` gives them (the text table names the roles and fields, as in brackets):

| Verdict | Meaning |
| --- | --- |
| `anyone reads sensitive fields` | The anonymous role reads passwords, secrets, keys or card numbers, at any depth of the JSON, or a token another session reads too, even when every role gets the same answer (`[anyone reads sensitive fields: password]`). |
| `reads another role's object` | A role reads the owner's object as the owner does (the same body, or the same fields around the same identifier) (`[bob, admin read alice's object]`); a made-up identifier on the same route is not answered alike. An owner inferred from the answers whose object the anonymous role reads alike is public instead. |
| `answers any identifier` | As above, but the route answered a made-up identifier as a real object too: its 2xx says nothing of who may read what (`[answers any identifier: bob read alice's object and a made-up 1000014 alike]`, `confidence` `guess`). |
| `every signed-in role reads the same object` | An object URL every signed-in role reads alike, owner unknown. |
| `roles read the same sensitive fields` | Several roles read the same values of sensitive fields: no session's own (`[alice, bob read the same sensitive fields: deluxeToken]`). A token only its own session gets is not listed. |
| `same answer for a session that did not find it` | A role that never reached the URL gets the answer the role that found it got. |
| `signed-in only` | The anonymous role is refused, every signed-in role reads it. |
| `only one role reads it` | Every other role is refused (`[only admin reads it]`). |
| `some roles refused` | Some signed-in roles read it, others are refused. |
| `different fields per role` | Every role reads it with the same status, with different nested fields. Fields under a list one role has empty are data, not fields; so is a field of a list's items that only holds true or false (`data[].liked`) and only one role gets. |
| `anyone reads the same object, signed in or not` | An object URL the anonymous role reads as the others do. Listed once per route (`-all`: every object). |
| `status differs` | Anything else (other redirects, 5xx). |

With `-all` also: `different data per role`, `same for every role`, `no role reads it`, `not answered`. The summary counts the verdicts of the rows listed; a note counts the endpoints compared and not listed (`58 more endpoints compared and not listed (34 same for every role, 23 no role reads it, 1 different data per role); -all lists them`).

Who each signed-in role is tells its own objects apart without `-id`: the claims of a JSON Web Token its headers or cookies carry (`sub`, `id`, `email`, `username`, `data.id`, …, and identifiers such as Juice Shop's `bid`), its own answer to a `/me`-like endpoint (`/me`, `/whoami`, `/userinfo`, …) when the anonymous role gets another, and, for `-role-login`, what the login answered and left in `localStorage` and `sessionStorage`. Each role's own objects are asked of every other role.

An identifier is a role's own only for objects of its kind, told by the route's noun (the path segment before the parameter), singular or plural, in any case. One the role's session holds fills a route when its name is that noun's: `basketId` and `basket_id` fill `/rest/basket/{id}`, `userId`, `uid` and the `id` of the user object in a token or a `/me` answer fill `/api/Users/{id}`. A short name, the initials of the noun's words (`bid`), fills it only when no other noun has those initials: not that of another route (`/api/books/{id}` beside `/rest/basket/{id}`: `bid` is neither's, and the session's value is tried on both as no one's object) nor that of a reference field the answers hold (`BrandId`). `bid` does not fill `/api/BasketItems/{id}` (`biid`), nor `/api/basketitems/{id}` beside a `basket` route. A short name alone is a guess: the object is the role's only if its own answer says so (see below). A list item whose own fields name a role is that role's object: an owner field (`owner`, `user`, `username`, `userId`, `email`, `createdBy`, …) that names the role, or a reference field that points at an object the role's session names. A reference field names its kind in full: `BasketId` 8 is alice's basket when her session holds basket 8 as `basketId`, or as `bid` while `bid` stands for the basket route alone; `BookId` 8 is not. An account, a customer or a member is not the user: `accountId`, `customerId` and `memberId` are reference fields, matched against the session's own `accountId`, `customerId` or `memberId`, never against its user id. Its identifier is the field the route's parameter maps to (`book_title` for `/books/v1/{book_title}`) or, in the route's own list or a list of the same noun, its `id`. An item of another kind lends its owner only to the object its owner or reference field points at (the `UserId` of an address fills `/api/Users/{id}`), not to the others it names (the `ProductId` of alice's basket item is not alice's product).

Once every role has asked an object, its own answer has its say on whose it is (the answer, or the object its envelope carries, such as `data`; the answers of every role that reads it must agree). An owner or reference field that names the owner confirms it; one that names a role makes an object no one owned that role's. Past that, it depends on what filled the route. An owner a short name alone gave (`bid`) goes unless the answer names that role, and goes to the role it names instead. An owner a list item or a field in the role's answers alone gave goes to the role the answer names, and goes altogether when a field's value is not that role's while its session holds one of the same kind and shape (a user id, an email, a basket id): `/api/BasketItems/8` with `BasketId` 5 is not alice's, though her `bid` is 8. An owner proved by an identifier the session holds under the route's full name (`basketId`, a user id) or by the role's own list (`/api/transactions` holds alice's transaction alone) stays, whatever another field says: alice's project in her other organisation is still hers, and an `accountId` equal to bob's user id does not make it bob's. Only a field that names another role by an identifier that role's session holds under the same name (its `email`, its user id as `UserId`) hands it to that role. A name is spelled too many ways to say an object is not the role's. An object given with `-id ROLE:…` stays that role's.

`-id [ROLE:]NAME=VALUE` (repeatable) fills routes with an identifier of your own: NAME is a path parameter (`book_title`), a JSON field that holds such values (`basket_id` and `BasketId` fill `/rest/basket/{id}`), or a route (`/rest/basket/{id}`). With ROLE, VALUE names that role's own object, so another role reading it is `reads another role's object`; without, it is tried like an identifier the answers held. Each route is also filled with up to 5 of each role's own identifiers (those who the role is names first) and 6 others, in order (numbers by value); the replay asks objects given with `-id` first, then the roles' own objects, then what the runs reached, then other objects, and takes a URL only while `-replay-max` holds every role's request for it.

A signed-in role whose session looks expired or wrong is named in a note, with what the site says when that role asks one such endpoint again: `role x was refused wherever a session matters (the site said "Signature expired. Please log in again."): its session looks expired or wrong; its rows show what a visitor gets`, and roles exits 3. It was refused on every endpoint the anonymous role is refused and another signed-in role reads, or on every endpoint another role reads, and it read no `/me`-like endpoint unlike the anonymous role. When no signed-in role reads anything the anonymous role is refused, as when tokens copied at the same time expire together, each is judged alone: refused on every endpoint the anonymous role is refused, and given nothing more than the anonymous role anywhere (a role that read an endpoint the anonymous role did not, or was forbidden, 403, where the anonymous role was asked to sign in, 401, is known to the site and alive). Every value the role sent (its headers, cookie values, the credential after `Bearer` or `Basic`) and anything shaped like a credential is taken out of the quoted reason.

A JSON Web Token a role sends as its credential (in `Authorization`, or a header or cookie named for one: `X-Auth-Token`, `token`, `jwt`, `session`, …; not an analytics cookie) is read for its `exp` before anything is sent. One that has expired is said at once on stderr, and the end of the run says what came of it: a dead session (`its token expired at …`), a site that still took it when it was the role's only credential (`role alice's token expired at …, yet the site still let it read 3 endpoints the anonymous role is refused: check that it verifies token expiry`, a finding), or, with nothing to tell, a note and exit 3. A token that expires within 15 minutes is noted too. For tokens that live minutes, `-role-cmd 'alice=./token.sh alice'` gives a role whose headers a shell command prints, one `Header: value` per line, or a bare token sent as `Authorization: Bearer`; the command runs before the role's run and again before the replay. `-role-cmd` is not offered over MCP.

A role given with `-role` sends those headers and nothing else, so behaviour an app ties to a cookie is not reached with a header alone: Juice Shop's `/rest/user/whoami` reads the `token` cookie, and answers `{"user":{}}` to an `Authorization` header. Give the cookie as one of the role's headers (`-role 'alice=Cookie: token=eyJ…'`, what `-cookie` sends in a run), or use `-role-login`, which carries the cookies and the token the login stored.

**Negative controls.** Each row where a role reads another role's object is asked again, by each of its readers, with a made-up identifier of the same shape on the same route: a number 1000003 past the real one, a random UUID for a UUID, a random string of the same length and the same kinds of characters for the rest (`/rest/basket/1000022` for `/rest/basket/19`). A route that answers it as a real object (2xx, not an error, not a refusal, the same body, or the same nested fields holding data besides the made-up identifier and what echoes it) answers any identifier, and the row becomes `answers any identifier`; a reader it answers so beside one it refuses is dropped from the row's readers. Each reader is asked once per route and shape of identifier; the controls count against what `-replay-max` leaves after the replay.

**Canaries.** A session can die during the replay (a token that lives minutes, a server that logs a session out). Each signed-in role's session is checked on an endpoint only a live session reads: `-canary [ROLE:]URL[=REGEX]` (without ROLE, for every signed-in role not given one of its own; with REGEX, a live session's body must match it), else its own `/me`-like answer, one of its own objects, or an endpoint the anonymous role was refused, never one the anonymous role reads alike (JSON first, then the shortest URL). It is asked before each role's replay, every `-canary-every` requests (50; 0: no checks) and after it, and must answer as the role's run got it (the same body, the same JSON fields, or the same page title). When a check fails, the session is renewed (`-role-cmd` run again, a new Chrome sign-in for `-role-login`; at most 5 times a role, and not again once a new session fails its first check) and what was asked since the last good check is asked again: `role alice's session failed its check (/api/Cards → 401) during the replay; its -role-cmd gave a new one, and the 50 requests asked since the last good check were asked again`. A session that cannot be renewed (`-role` headers) or does not come back leaves the answers asked after its last good check `session_suspect`, with a note (`role bob's session failed its check (/me → 401) during the replay and did not come back: 31 answers asked after it was last seen alive (session_suspect)`). A signed-in role with nothing to check it by is named in a note. The checks and the requests asked again count against `-replay-max`.

**Refusal pages.** Some sites refuse with a 2xx page. Each origin's is learned from what the anonymous role got on endpoints a signed-in role reads otherwise: a 2xx answer whose title and first heading, or JSON message, says so (`Access denied`, `Forbidden`, `Please sign in`, …: one endpoint is enough), or asks to sign in on two endpoints or more. It is told by its status, what it says, its JSON fields and, when it does not change, its body's hash; every role's 2xx answer that matches it counts as refused (`200:refused` in the text table), and a note names it (`http://app refuses with a 200 page saying "Access denied" (the anonymous role got it on 3 endpoints a signed-in role reads otherwise): such an answer counts as refused for every role`). `-refusal REGEX` says what a refusal body looks like when the page does not say it in words: every 2xx answer whose body matches is refused, for every role.

**Evidence.** The answers behind the rows listed are kept in `roles.db` in `-dir`: each role's answer to each row (and to its control), its body gzipped and cut at 256 KB, with the values of sensitive fields (passwords, tokens, keys, secrets), JSON Web Tokens and every value a role sent (its headers, cookie values, the credential after `Bearer`) replaced by `[redacted 1a2b3c4d]` (the same value shows the same tag within a run; the tag tells nothing of it). A role may not be named `roles`. `azhaq roles show -dir DIR URL [-method M]` prints one row: its verdict, `confidence`, `evidence` and `owner_by`, then per role its status, length and type, a curl line that asks it again with the role's session as a shell variable, never its value (`-H "Authorization: Bearer $ALICE_TOKEN"`, `-b "$BOB_COOKIE"`, `-H "X-Api-Key: $BOB_X_API_KEY"`), and how its body differs from the owner's (or the first role's that reads it) field by field: `- data.id  19` (the owner's only), `+ detail  "No authorization token provided"` (this role's only), `~ user.name  "alice" → "bob"`, at most 20 lines. `-method PUT` picks a write's row, `-body ROLE` prints the body ROLE got as kept and nothing else, and `-json` gives the row and each answer with its `curl` and `diff`. The curl lines need the variables set to the sessions the roles sent; roles keeps none of them.

With `-json`, stderr holds the summary only: the runs of the roles print nothing, and what they did not finish is in it (`failed`, `unreachable`, `skipped`, `notes`; a role's run stopped by a limit is `stopped`, exit 4). A role whose run could not be done (a failed sign-in) ends roles with a summary whose `notes` say why.


### History (`-har`, `-burp`)

- `-har NAME=FILE`, `-burp NAME=FILE` (repeatable; the same NAME adds files): the requests account NAME sent, as a HAR (browser devtools, Caido, Burp) or a Burp "Save items" XML file. NAME is a `-role` of that name or a new role.
- Session: a role with no `-role` headers (and no `-role-cmd` or `-role-login`) takes the Authorization and Cookie header of its most recent request to the target. `Bearer null` and `Bearer undefined` are no session; a role whose history carries none is anonymous.
- Target origins: for each account, the origin most of its requests go to, and any other with a quarter of them; `-allow HOST` adds one. Requests to other origins (analytics, CDNs) are neither sent nor read from, and a note names them.
- Pages: each GET on the target that does not look like it changes something is asked once, as the account, and its answer is the account's own, as if its run had found it. `/rest/basket/6` and `/rest/basket/7` in two histories are the route `/rest/basket/{id}`. Replay, identity, controls, evidence and `roles show` work as after a crawl.
- Without `--` run options nothing is crawled and the target is the history's origins; with them, the crawl's pages are added. `-no-anon` leaves the anonymous role out; `-rate N` paces the history reads and the replay. The history reads count against `-replay-max`.
- With `-replay-writes`, the history's writes of the methods named are replayed, to the target's origins only, never a logout, DELETE only when named. A write is proved in the field it sets, against the object as the owner's last write left it; a short 2xx answer that says no (`Only Admins may delete users!`, `forbidden`) is a refusal.

### Writes (`-replay-writes`)

`-replay-writes METHODS` (`post`, `put`, `patch`, `delete`, comma-separated) also asks each role's writes with every other role's session, after the reads. Writes change data on the target: they go only to the hosts of the run options' `-url` values, or to the scope `-allow` or `-scope` names. The writes are:

- the ones a role sent, from a HAR (`-har NAME=FILE`, as a browser's developer tools or Burp save it): its requests with those methods on the run's hosts, one each, with their bodies and `Content-Type`, `Accept` and `X-Requested-With`, never the session that sent them (cookies, `Authorization`, a CSRF token); a logout is never replayed;
- the PUT, PATCH and DELETE that the routes the runs found take (from API descriptions and scripts), on each role's own objects, filled with each role's own identifiers (the same identity the read replay uses: JWT claims, `/me` answers, list items, `-id`) — including routes that only take a write and have no GET (`PUT /users/v1/{username}/email`): PATCH with an empty JSON object, which asks for the write and changes nothing; PUT with an empty JSON object, which changes nothing on a server that updates the fields sent but may clear the owner's own object on one that replaces it on PUT; DELETE with no body. A route whose write takes a form, and a POST (which creates in a collection), are left to the HAR.

**A cross-role write is claimed only when it is proven.** Before and after another role's write, the owner's object is read again as the owner — the write's own URL for a PUT, PATCH or DELETE on an object, or, for a write whose URL is not readable (`/users/v1/alice/email`), a readable ancestor (`/users/v1/alice`, which shows the email). `writes another role's object` is reported only when the owner's object changed the way the write asks (one of the body's values is now in it), or was deleted. A write answered 2xx that left the owner's object unchanged (an app that writes the caller's own object whatever the path says) is `answered 2xx but changed nothing of the owner's`, not a finding. A POST to a collection is never a cross write: a role let to send it `creates in another role's collection`.

A map write (empty body) is first sent with its owner's session; when the owner is let, its object is read again, and if a value it held changed (timestamps aside) nobody else is asked (`the owner's own write was refused`). Then the anonymous roles, then the other signed-in roles; a DELETE goes to the others alone, the anonymous role first, and stops at the first proven. A write is let when it is answered 2xx and not with an error shaped as data; it is proven by the owner's object changing. Proved cross writes keep the top of the list, above the reads; the unproven rows (`answered 2xx but changed nothing`, `creates in another role's collection`) rank below the proved reads. Every request — each write and each read of the owner's object to verify it — counts against `-replay-max` (what the read replay left) and the run's `-max-requests`, at the run's `-rate`, and is sent without following a redirect.

| Verdict | Listed | Meaning |
| --- | --- | --- |
| `anyone writes another role's object` | yes | the anonymous role's write changed the owner's object (proven) |
| `writes another role's object` | yes | a signed-in role's write changed the owner's object (proven; `readers`) |
| `writes another role's object: accepted; the change cannot be read back to confirm` | yes | another role's write on the owner's object was answered 2xx (the row says which, `accepted (204)`), and no GET of the owner's object shows the field it sets (VAmPI's `PUT /users/v1/{username}/password`: `/users/v1/alice` has no password), or the object cannot be read at all. Neither proved nor disproved: check it by hand. Never reported as "changed nothing" |
| `would be sent (-dry-writes)` | yes | `-dry-writes`: nothing was sent |
| `answered 2xx but changed nothing of the owner's` | `-all` | a role was answered 2xx, but the owner's object did not change the way the write asked, or could not be read to verify it: not a finding, check by hand |
| `creates in another role's collection` | `-all` | a POST a role was let to send: a create, never another role's object written |
| `only its owner writes it` | `-all` | the others were refused |
| `the owner's own write was refused` | `-all` | the owner was not let, or its empty write changed its object: nothing to compare |
| `the other roles were refused` | `-all` | a DELETE (never asked of its owner) that no other role was let to send |
| `the other roles' writes failed with a server error (5xx): neither refused nor accepted` | `-all` | every other role's write was answered 5xx (a unique key the server already held, a crash): nothing is said about who may write |

The row's `owner_by` says where the write came from (`alice.har`, `PUT /api/BasketItems/{id} with an empty body`) and what proved it (`after bob's PUT the owner's object changed to match it`, `after bob's DELETE the owner's object is gone (404)`); `confidence` is `proved` on a proven cross write; `evidence` says who was let; `azhaq roles show -dir DIR -method PUT URL` prints each role's curl line with the write's body.

## report

`azhaq report -dir DIR` writes up what `azhaq roles` found as one Markdown report per finding, ready to paste into HackerOne or Bugcrowd, or into a red team's client report. It reads the evidence the roles run kept in `DIR/roles.db` and sends nothing.

```
$ azhaq report -dir azhaq-roles-20261028-101500
azhaq report: 3 reports in azhaq-roles-20261028-101500/reports
  …/01-proved-get-books-v1-book-title.md  [proved] Broken object level authorization: bob reads alice's book via GET /books/v1/{book_title}
  …/02-proved-get-books-v1-book-title.md  [proved] Broken object level authorization: alice reads bob's book via GET /books/v1/{book_title}
  …/03-unrated-get-users-v1-debug.md  [unrated] Excessive data exposure: anyone reads password via GET /users/v1/_debug
```

Without `-url`, it writes a report for each listed row whose verdict is `reads another role's object`, `writes another role's object`, `anyone writes another role's object` or `anyone reads sensitive fields`, ordered by confidence (`proved`, `likely`, `guess`, then rows that carry none). With `-url URL` (and `-method M` for a write row) it writes that one report to standard output; a row that is not one of the four verdicts is refused.

| Flag | |
| --- | --- |
| `-dir DIR` | the `-dir` of the roles run (it holds `roles.db`) |
| `-url URL`, `-method M` | one row only |
| `-format md\|json` | Markdown (default), or the same content as structured fields |
| `-o PATH` | a file (the reports one after another, a JSON array for `json`), or a directory (`out/`, or an existing one) with a file per report; default: `DIR/reports` |
| `-redact` | also mask hosts (`<host>`) and identifiers (`<id-1>`) |

Each report has a title naming the bug class (broken object level authorization for a read, "(write)" for a write, excessive data exposure for sensitive fields anyone reads), a two-sentence summary, a severity that is labelled a guess and says why (sensitive fields and a write raise it), numbered steps with the curl commands from the evidence (the sessions as `$ALICE_TOKEN`, `$BOB_TOKEN`), the evidence (status, length and the relevant JSON fields of the owner's answer, the reader's, and the control: what a made-up identifier returned), the row's `owner_by` quoted as the reason the object is the owner's, impact and remediation by class, and notes (confidence, both ways, "found by azhaq roles, run DATE").

A report never says what the evidence does not hold. A row with no control, a body that was not kept, no `owner_by`, or an evidence file from an older azhaq (no run date) says so in the report, under "Missing from the evidence store". A write's before-and-after reads of the owner's object are not kept; the report says so.

`-redact` is for a report that leaves the engagement: the host becomes `<host>`, the identifier in the route and the values of identifier fields in the kept bodies (`id`, `*Id`, `username`, `owner`, `email`, …) become `<id-N>`, and any token is removed. Role names are the tester's own labels and stay. Read a redacted report once before sharing it: an identifier no kept body names in an identifier field is not masked.

`-format json` holds, per report: `title`, `class` (`bola_read`, `bola_write`, `excessive_data_exposure`), `method`, `url`, `route`, `verdict`, `confidence` (`unrated` when roles gave none), `summary`, `severity_guess` (`level`, `reason`), `variables`, `steps` (`n`, `text`, `curl`, `expect`), `evidence` (per answer: `role`, `kind` `owner`, `reader`, `other` or `control`, `request`, `status`, `length`, `content_type`, `body_kept`, `fields`), `owner_reason`, `impact`, `remediation`, `notes` (`confidence`, `both_ways`, `found_by`, `run`) and `missing`.

## diff

A web page's answer is compared by status and title, and a JSON listing's also by how many items it holds (`json_items`): `watch` reports `/users/v1: [200] 5 items → [200] 6 items`. Bodies are not compared byte for byte: timestamps and tokens would make every run a change. A workspace with one run says so: a diff needs two.

`diff -jsonl` prints `added` and `removed` rows, `not_seen_again` rows and a `summary`. `removed` is what answered in the older run (a name that resolved, a page with a status, a host with open ports) and is gone from the newer. `not_seen_again` is what the older run only heard of (from a subdomain source, an archive, a link) and never checked: sources answer differently from day to day and fail, so its absence says little. The summary names the `failed_sources` of the newer run.

## watch

`azhaq watch -db FILE -- RUN FLAGS` runs the run options into the workspace and compares its last two runs, in the terms a person watching a target cares about. The text names each kind of change that happened, with at most 20 lines each (`… and N more`), and says `no change` when nothing did. The first run of a workspace is the baseline: everything in it is new, and it lists no routes. The baseline is printed but not sent to `-notify` or `-notify-cmd` (`-always` sends it, and every run after it).

```
azhaq watch app.db: 2026-10-29 23:29:48 against 2026-10-29 23:29:48
~ 4 API routes
    + POST /api/v2/export {format, userId}  (main.js)
    ~ /api/orders/{id}: +DELETE  (main.js)
    ~ PUT /api/profile: +role  (main.js)
    - /api/legacy/report  (main.js)
```

The sections are `+ hostnames that resolve`, `+ web services`, `+ URLs`, `~ API routes`, `~ hosts whose open ports changed`, `~ pages that answer differently` and `- hostnames gone`, `- web services gone`, `- URLs gone`. A frontend deploy that adds a route adds attack surface, and the first report is the one that pays, so the `API routes` section ties each change to the script that calls the route:

- `+ METHODS /route {names}`: a new route, its methods and the names it sends (query and body). The names are read from `fetch`, `XMLHttpRequest` (`send`), axios and jQuery calls whether the body is written in the call or kept in a variable, `JSON.stringify(…)`, `URLSearchParams` or a `FormData` built with `append`. A route that a script only names in a string, with no call and no description, has no method on its line (`+ /api/ping`): azhaq says no GET it did not see.
- `~ /route: +DELETE`: a method added to a known route (or `-GET`, removed).
- `~ PUT /route: +role`: a name the route's call now sends (or the name with a `-` in front, removed).
- `- /route`: a route the previous run's scripts or API description named and no source names in this run.

A route only found by guessing or in an archive is never reported gone, and one a crawl or a guess finds is not reported new: routes are compared where a script or an API description names them. Placeholder names (`{id}` or `{orderId}`), identifiers, ordering and case are not changes, so the same app mapped twice reports no route change; a placeholder renamed is no `URLs` or `URLs gone` line either. The start of a path a script joins more to (`"/api/admin/users/" + id + "/reset"` names `/api/admin/users/{id}/reset`, not `/api/admin/users`) is no route and is never reported. A route that answers differently (status, title, item count) stays under "pages that answer differently". A route reported as new or gone is not repeated under "URLs".

Notifications. `-notify URL` posts the text to a webhook: Slack and Discord incoming webhooks and Telegram's `sendMessage` (with `?chat_id=`) get it in their own shape, any other URL gets `{"text": …, "data": the change set}`. `-notify @FILE` reads the URLs from a file, one a line (`#` comments), and `$AZHAQ_NOTIFY` holds more, comma-separated; neither puts a URL on the command line. `-notify-config FILE` sends to the providers of a [notify](#notify) `provider-config.yaml` instead (`-notify-provider` and `-notify-id` pick entries). The text lists up to `-notify-lines` lines (default 100) of each kind of change and counts the rest; the terminal shows 20. A message longer than the service takes (Discord 2,000 characters, Telegram 4,096, Slack 40,000) goes out in parts labelled `(1/3)`, cut at a line or a space. `-notify-format` sets the message with notify's variables (`{{data}}`, `{{date}}`, `{{time}}`, `{{datetime}}`, `{{count}}`), `-notify-rate` paces the requests (default 1 a second) and `-notify-proxy` sets a proxy. A URL's query sets what the service lets a message carry: `username` and `icon_emoji` for Slack, `username` and `avatar_url` for Discord, `parse_mode`, `thread` and `preview=yes` for Telegram. A 429 or a 5xx, or a connection that failed, is tried again (three tries, waiting for `Retry-After` up to a minute); any other 4xx is not. A delivery that failed is printed on stderr as `azhaq watch: POST https://host/…: reason`, never with the URL, and the exit code is 3 (the run's own 3 or 4 wins). With `-json` (and for `-notify-cmd` and generic hooks) the change set is one JSON object: `db`, `run`, `previous`, `baseline`, `hosts`, `services`, `urls`, `ports`, `changed`, `gone_hosts`, `gone_services`, `gone_urls` and `routes`. A `routes` entry is:

```json
"routes": [
  {"kind": "new", "host": "app.example.com", "route": "/api/v2/export",
   "methods_added": ["POST"], "fields_added": ["format", "userId"],
   "script": "https://app.example.com/main.js"},
  {"kind": "methods", "route": "/api/orders/{id}", "methods_added": ["DELETE"], …},
  {"kind": "fields", "route": "/api/profile", "method": "PUT", "fields_added": ["role"], …},
  {"kind": "gone", "route": "/api/legacy/report", "methods_removed": ["GET"], …}
]
```

`kind` is `new`, `methods`, `fields` or `gone`; `script` is the first script that names the route; `methods_removed` and `fields_removed` are set when something was taken away.


## notify

`azhaq notify` is [notify](https://github.com/projectdiscovery/notify): it reads text from standard input or `-i FILE` and sends it to the providers of a `provider-config.yaml`. Its flags are notify's, long and short (`-provider-config/-pc`, `-data/-i`, `-provider/-p`, `-id`, `-rate-limit/-rl`, `-delay/-d`, `-bulk`, `-char-limit/-cl`, `-msg-format/-mf`, `-silent`, `-verbose/-v`, `-proxy`, `-config`); `-no-color` and `-disable-update-check` are accepted and do nothing. The config is notify's schema, key for key, from `-pc`, else `~/.config/azhaq/notify.yaml`, else `~/.config/notify/provider-config.yaml`. A word that starts with `$` is replaced by that environment variable when it is set, and a key the schema does not have is an error (exit 2), so a mistyped `slack_webhok_url` is not a silent hole. `-config FILE` (or `~/.config/notify/config.yaml`, when it exists) holds the flags by their long names; a flag on the command line wins.

Messages are cut as notify cuts them: one per line, or with `-bulk` as many lines as fit in `-cl` characters (default 4000); a line over the limit goes out in pieces of `-cl` minus 3 that end in `...`, none cut inside a character. An empty line is no message. `-d` waits that many seconds before each message and `-rl` (default 1) is the most requests a second, for every provider (0: no limit). Each message goes to every entry of every provider, in the order slack, discord, pushover, googlechat, smtp, teams, telegram, custom, gotify; `-p` and `-id` narrow them (a name that is no provider, or a filter that matches nothing, is exit 2: nothing would be sent). Colour codes are removed. `-mf` (or the entry's `*_format`) sets the message: `{{data}}` is the text, `{{date}}` is `01-02-2006`, `{{time}}` `15:04:05-0700`, `{{datetime}}` both, `{{count}}` the number of messages the provider has sent (notify's Discord and custom providers leave it at 0; azhaq counts).

| Provider | What is sent |
| --- | --- |
| `slack` | webhook (`slack_webhook_url`, must start `https://hooks.slack.com/services/`): `{"text", "username"?, "icon_emoji"?}`. With `slack_threads`: `POST https://slack.com/api/chat.postMessage` with `Authorization: Bearer slack_token`, `{"channel", "text", "thread_ts"?}`; the first answer's `ts` is the thread of the messages after it (a failed `ok` is an error). |
| `discord` | `https://discord.com/api/webhooks/ID/TOKEN`: `{"embeds":[{"description","color"}], "username"?, "avatar_url"?}`, 2,000 characters to an embed, at most three embeds to a post, more posts for more text. With `discord_threads`: `{"content","username"?,"avatar_url"?}` to the URL with `?thread_id=`. |
| `telegram` | `https://api.telegram.org/botTOKEN/sendMessage`: `{"text","chat_id","message_thread_id"?,"parse_mode"?,"disable_web_page_preview","disable_notification","reply_to_message_id"}`; `telegram_chat_id` may be `chat:thread` or a comma list; a text over 4,096 characters goes in parts (notify refuses it). |
| `pushover` | `POST https://api.pushover.net/1/messages.json`, form-encoded `device`, `user`, `token`, `message`, `priority=0`; 1,024 characters to a message. |
| `googlechat` | `POST https://chat.googleapis.com/v1/spaces/SPACE/messages?key=…&token=…`: `{"text"}`; 4,096 characters to a message. |
| `teams` | an Office 365 connector (`…/webhookb2/…`): a `MessageCard`, one section a line, answered 200; a Power Automate workflow (`…/workflows/…`): `{"text"}` with HTML escaping and `<br>`, answered 202. |
| `smtp` | one mail to each address of `smtp_cc`, in one session: STARTTLS when the server offers it (and `smtp_disable_starttls` is not set), PLAIN authentication with `smtp_username`, implicit TLS on port 465; `smtp_server` is `host` or `host:port`. With `smtp_html` a plain and an HTML part. |
| `gotify` | `POST /message` with `X-Gotify-Key`: `{"message","title"?}`; a token of the old shape (15 characters, starting with `A`) goes in the query with notify's default title and `priority`. `http` with `gotify_disabletls`, `https` otherwise, with the certificate checked. |
| `custom` | `custom_method` (GET when empty, as in notify) to `custom_webhook_url` with `custom_headers`; the body is the message, the `custom_format` with `{{dataJsonString}}` (the message as a JSON string), or a `custom_sprig` template over the message read as a JSON object (`{{ .url | upper }}`, [Sprig](https://masterminds.github.io/sprig/) functions). An answer of 300 or more is a failure; notify does not look. |

Every request has 30 seconds. A 429, a 5xx or a failed connection is tried again, up to three times, waiting for `Retry-After` (seconds or a date, up to a minute; a longer one is reported, not waited out) or 1 and 2 seconds; any other 4xx is not tried again, and a redirect to another host is not followed. Failures are never silent: the summary lists each provider and the ids of its entries that did not get a message, with the reason (`custom failed: POST http://host/…: 500 … (after 3 tries) ×4 (id ops)`), `counts` has `delivered` and, when any message needed more tries, `retried`, and the exit code is 3, where notify prints a line and exits 0. No error holds a URL's path or query, or a token, key, password or header value of the config, even if the server repeats it.

## query, show, plan, ingest

- `query -json` prints map rows (as `run -json`, with `found_in`), or only the `-fields` asked for; every row that matches, unless `-limit` says otherwise (the summary then says how many matched). `query -failed` prints every failed target instead: `target`, `collector`, `source`, `error`, `retryable`.
- `show -json` prints one object: `row` (the map row, with `found_in`), `links` (`rel`, `dir` in or out, `type`, `key`) and `observations` (`collector`, `kind`, `source`, `observed_at`, `payload`; an `azhaq-js` observation's payload holds the `found_in` of the page it read); for a hostname, `services`: its front pages with `coverage`, `status`, `title`, and the `error` of one that failed. A GraphQL endpoint read with `-graphql` has an `azhaq-graphql-schema` observation whose payload holds `queries`, `mutations`, `subscriptions` and `types` (names) and `schema`, the introspection's whole `__schema` object (past 8 MB without its descriptions; past that left out, with its size in `schema_bytes`). A server that refuses the full introspection query for its depth is asked for the names only, and `schema` is absent. A server with introspection turned off is asked for root fields by name, as clairvoyance does: its validation errors (`Cannot query field "pastez" on type "Query". Did you mean "pastes"?`, `Field "paste" of type "PasteObject" must have a sub selection`, required arguments) give the payload `queries`, `mutations`, `types` and `signatures` (`uploadPaste(content: String!, filename: String!): UploadPaste`), with `"recovered":"suggestions"`. That is not the server's schema: it lacks types, fields it never suggested, and the types of fields whose errors did not name them. The exports mark it as partial (below), and a whole schema read by introspection is not marked. Every document asked carries a field no schema has, so none passes validation and nothing runs. A GraphQL endpoint found by a run (an `azhaq-graphql` observation) has `get_queries` true when it answers `{__typename}` sent with GET.
- `plan -json` prints one object: `targets` (each with the collectors that would run on it), `skipped`, `collectors` (what each does to whom), `active`, `builtin_paths`, `limits`, `sends`, and `requests`: what is known of the requests before any is sent. `source_queries` counts, per collector, the queries to third-party sources about the targets listed (one per source asked; a source may page through its answer), `source_queries_total` adds them up, and `source_queries_not_counted` names the collectors that do not say before they run which sources they ask (none of the built-in ones; a connector may not). `found_domains_asked` is true when domains found on the way would be asked about too (inside the scope; without one, within `-depth` and `-max-items`). The requests to the targets are a bound, not a count: how many names resolve and answer is known only by asking (`max_names` of them at most are looked up). `per_web_service` is about what each web service costs before its links, scripts and archived URLs are followed (its page, the favicon, the built-in paths), and `cap` the requests to the targets at most, set by `cap_by` (`-max-requests`, or `-daily-requests`, of which a plan does not take off what the day's runs spent); 0 is no cap. `passive` is true when nothing goes to the targets.
- `ingest` prints only its summary: `results` is the facts read (of every file given), `counts` the lines read per format. Files are arguments (`azhaq ingest a.jsonl b.jsonl`), `-` is stdin, and `-in FILE` still works.

## hunt

`azhaq hunt -db FILE [-roles roles.jsonl] [-limit 25] [-since 168h]` ranks the mapped routes, hosts and files by what a tester should open first. It reads the workspace and sends nothing. One row per route template: a key with `{n}`, `{uuid}`, `{hex}` or `={v}` is a template folding several URLs, and a key seen once is the URL itself.

- Text: one row per line, `rank  score  key  reason; reason  → next: COMMAND`. A reason is `signal: detail`.
- `-json`: one object per row: `rank`, `score`, `key`, `type` (`URL` or `Hostname`), `reasons` (an array of `{signal, detail}`) and `next`. The summary on stderr counts `rows`, and a note says how many rows had a signal when `-limit` cut the list.

The score is the sum of the row's signals, each counted once at its highest weight. A row with no signal of its own is left out; one whose only signal is `new` never ranks. Static assets, scripts, catch-all pages and pages that are gone are never rows. Ties go to the target before fan-out, then to the row with more distinct signals, then by key. `-roles` reads the JSONL `azhaq roles -json` printed (repeatable); `-since` is how long ago a row is first seen to count as new, and `new` is added only when the workspace also holds URLs older than that.

| Signal | Raised by |
| --- | --- |
| `cross-role` | a `-roles` verdict that one role reached another's data: `reads another role's object`, `writes another role's object`, `anyone writes another role's object`, `anyone reads sensitive fields`; the weight is scaled by the row's confidence (`proved` whole, `likely` 85%, `guess` 60%) and the reason quotes its evidence |
| `takeover` | a name another party may take over (`strong` weighs more than `dangling` and `page`) |
| `secret` | a credential a script carries, weighed by its severity; the file is named |
| `sourcemap` | a source map served |
| `exposed-file` | a `.kdbx`, `.pem`, `.key`, `.env`, `.sql`, `.db`, `.bak`, `.old`, `.orig`, `.swp`, `.zip` or `.tar.gz` file, or a `.git` directory, served; named or refused, it weighs less |
| `listing` | a directory listing |
| `api-description` | an API description served |
| `graphql` | a GraphQL endpoint, whose schema was read, or whose IDE answers (weighs more), or that answers like GraphQL |
| `object-id` | `{name}` in the path, or an `id` parameter; a route with no GET weighs less |
| `unauth-write` | POST, PUT, PATCH or DELETE that no description asks credentials for, on a route that did not turn the plain request away; it weighs less when no GET showed that it answers |
| `upload` | a file field in a form, or an operation whose body is `multipart/form-data` or a file |
| `xml` | an operation whose body is XML (`application/xml`, `text/xml`): a parser that may read entities |
| `state-change` | a GET left alone because its name says it changes something (a logout is left out) |
| `password-in-url` | a GET form with a password field: it lands in logs and history |
| `gated` | a 401 or 403: a session is needed, a target for `azhaq roles` |
| `server-error` | a 5xx, by what shows beside it: SQL error text in the body (50), a framework's debug page (35), a parameter whose value came back (30), a stack trace (25; 15 when the request lacked the input the route takes), another role's answer to the same route (a 5xx for one role, an answer for another: 40). Alone it weighs 10, and 3 when the plain request carried none of the input the route takes (the row's `answer` is `500 without input`): a lead, not a finding |
| `input` | the route takes query, body or form names (more when a write sends named fields) |
| `new` | first seen within `-since` |
| `path-auth`, `path-search` | a word in the path says it signs in or issues a session (`login`, `signin`, `auth`, `oauth`, `sso`, `token`, `reset`, `forgot`, `register`, `2fa`, …: 45), or searches and filters (`search`, `find`, `filter`, `query`, `lookup`: 35). A route that a script or a description gives methods for counts in full even when it was not asked; a named route nobody calls weighs half |
| `param-command`, `param-url`, `param-file`, `param-debug`, `param-redirect`, `param-query`, `param-callback` | a parameter name that says what it takes |
| `path-admin`, `path-debug`, `path-config`, `path-env`, `path-doc`, `path-function`, `path-data` | a word in the path says what the route is for; the first five also read the labels of a host name that resolves |

`next` is a real command, chosen by the signal that weighs most in the row: `azhaq roles show -dir /abs/azhaq-roles-… URL` (with `-method` for a write) for a `cross-role` row, with the `-dir` of the roles run that listed it (the row's `dir`, else the folder of the `-roles` file when it holds `roles.db`, else the newest `azhaq-roles-*` folder of the current directory; when none is found the row's command is `azhaq show`); `azhaq roles -role anon -role 'user=Authorization: Bearer …' -- -url ORIGIN/` for `object-id`; `azhaq params -u URL -w WORDLIST` for `input`; `azhaq show -db FILE URL` for the rest.

## ledger

Every run with a workspace writes `DB.ledger.jsonl` next to it (`-ledger FILE` writes it elsewhere, `-ledger off` not at all; a drop-in command without `-db` writes one only with `-ledger FILE`; `azhaq roles` writes `roles.ledger.jsonl` in its `-dir`). It has one JSON line for each request or connection sent to a target, and `azhaq resume` and later runs into the workspace append to it. A run that ends writes a last line of kind `seal`, so lines cut from the end of the file show. DNS queries and third-party sources (the RDAP registry too) are not targets and are not listed. A line has:

| Field | Meaning |
| --- | --- |
| `seq` | the line's number, from 1 |
| `time` | when it was sent, UTC |
| `kind` | `http`, `tcp` (a connect of `ports`, or a TLS handshake of `ports` or `azhaq-tls`), `udp`, `chrome` (a request Chrome sent, listed once it left: one Chrome dropped before sending is not, nor counted; a WebSocket handshake is `ws://host:port/path?query`, and `wss://host:port` inside TLS), or `seal`: the end of a run, with no target |
| `method` | the HTTP method (not on `tcp` and `udp` lines) |
| `target` | the URL as sent, query string included (a password in its user info is masked), for `http` and `chrome`; `ip:port` for `tcp` and `udp` |
| `host` | the host the request was for |
| `rule` | the scope rule that allowed it (`-allow`, `-scope`); empty when the run has no rules |
| `collector` | what sent it, for the lines that say |
| `prev`, `hash` | the previous line's hash, and the hex sha256 of `prev` and this line's JSON without `hash` |

`azhaq ledger -verify FILE` prints the number of entries and runs, whether the chain is intact and the hash of the last seal: exit 0 when it is intact and ends with a seal; exit 3 naming the first line that is not intact (`line 3: hash does not match the content: the line was edited`), or, when lines follow the last seal, saying how many (`NOT SEALED: the last 9 were written after the last seal`: a run killed, crashed or still running, or lines cut from the end). Lines cut back to an earlier seal leave a sealed file: compare the last seal with the one the run's summary names. `-summary FILE` and `-csv FILE` leave the seals out. `-summary` counts the lines by `kind`, `method`, `host` and `rule`, with the first and last time (`-json`: one object, `entries`, `file`, `first`, `last`, `kinds`, `methods`, `hosts`, `rules`). `-csv FILE` prints one row per line with the columns `seq`, `time`, `kind`, `method`, `target`, `host`, `rule`, `collector` and `hash`. A summary of a run that wrote a ledger has the note `ledger: N requests and connections recorded in FILE, sealed HASH (azhaq ledger -verify FILE)`.

`-kill-file PATH` (default `DB.stop`; `roles.stop` in the `-dir` of `roles`, which stops the runs of the roles but not the replay after them) is the kill switch: the file is looked for every 100 ms, and once it exists nothing more is sent, not even a request already waiting for `-rate`. The run exits 4, and its `stopped` says `the kill switch: kill file PATH exists, N tasks known and not done (remove it, then azhaq resume)`. A drop-in command without `-db` has no default kill file.

## export

`azhaq export -db FILE -format F` writes the newest run of a workspace in one format on stdout.

| Format | Output |
| --- | --- |
| `jsonl` | Everything: one object per map row (`"kind":"entity"`, with `evidence` and `evidence_from`), observation and edge. |
| `urls`, `hosts`, `names`, `targets` | One per line: every URL; names that resolve, and addresses given as targets or serving the web; every name; web services (front pages that answered, Azhaq's or taken in from httpx, katana or ffuf), for `nuclei -l` and `httpx`. |
| `openapi` | OpenAPI 3 JSON of one origin (`-origin`, default the one with the most API routes): the description the target serves, as it is, plus the routes scripts call, forms, the pages found with a query string of their own (a GET taking those names) and what answered. A route the run left alone (`skipped`) has no GET or HEAD of azhaq's making in it: a tool importing the description would send one. Where the served description lists such a route anyway (VAmPI's `GET /createdb`), or azhaq guessed its POST, each operation carries `x-azhaq-skipped: true` and `x-azhaq-skipped-reason` (`looks like a GET would change something (createdb)`), and `-safe` leaves those operations out, for a tool that must not touch them. A GET form's fields are query parameters of its action's GET; a POST form's are its request body, `application/x-www-form-urlencoded` or `multipart/form-data` as its `enctype` says, a file input `"format":"binary"`. A form adds the fields an operation the export made lacks; a served description's operations are left as they are. `x-azhaq` on each operation: `source`, `coverage`, `status`, `needs_credentials`; `x-azhaq-evidence` beside it is the level of the route (a served description's operations are `described`, a form's `linked`). |
| `graphql` | The introspection result of each GraphQL endpoint read with `-graphql`, as InQL, Burp, Postman, graphql-voyager and clairvoyance read it. A schema recovered from validation errors has `"x-azhaq": {"introspection": false, "recovered": "suggestions", "partial": true}` beside `data` (inside each endpoint's object when several are keyed by URL), with `validation_errors`, `client_operations` and `untyped_fields` when known. |
| `sdl` | The same schemas in the GraphQL schema language. A schema recovered from validation errors, not read by introspection, starts with `# introspection disabled on URL; recovered from N validation errors and M client operations: partial, may lack types and fields`, then the root types as far as they were recovered; fields whose type was not recovered, and the client operations found in scripts, are listed in comments. |
| `burp` | Burp Suite project options with the run's target scope. |
| `html` | One self-contained page: web services, names, screenshots (embedded, 560 pixels wide; the page opens from any directory), secrets, API routes (with an Evidence column), the map. A picture file missing from where the run named it and from beside the database is listed as not found. For thousands of pictures use `azhaq gallery`, the interactive view (see [gallery](#gallery)). |
| `graphml` | The graph for Gephi, yEd or Cytoscape. |
| `secrets` | Credentials found in scripts: severity, kind, value, script, tab-separated. |

A format that finds nothing writes nothing and says why on stderr (`azhaq export: nothing to write: the workspace holds no host names (a run of a URL or an address has none: …)`); the exit code is 0.

**openapi** is a valid OpenAPI document whatever went into it: every operationId is unique (a served description's keep theirs; a repeat, such as `/blog` and `/blog/` both `get_blog`, gets `_2`, `_3` in path order), templates that differ only by their parameter names are one path (the served description's, else the first), every `{name}` in a path is a declared path parameter, a parameter is listed once, and component names OpenAPI does not allow are renamed with their references. A GraphQL endpoint is one `POST` taking `{"query","operationName","variables"}`, not a made-up REST mapping; its operations are in `x-azhaq-graphql`: An API route left alone for its name (`/user/change-email`) whose callers do not say the method is described as a POST, with `x-azhaq.method` saying it is a guess; never as a GET.

```json
"x-azhaq-graphql":{"operations":[
  {"type":"query","name":"pastes","arguments":[{"name":"public","type":"Boolean"},{"name":"limit","type":"Int"}],"returns":"[PasteObject]"},
  {"type":"mutation","name":"createPaste","arguments":[{"name":"burn","type":"Boolean","default":"false"}],"returns":"CreatePaste"}]}
```

`type` is `query`, `mutation` or `subscription`; `default` is a GraphQL literal; `deprecated` is set on deprecated fields. A schema kept by names only gives `type` and `name`. A schema recovered from validation errors (see `show`) adds `"introspection": false, "recovered": "suggestions", "partial": true` beside `operations`, and the text map puts `GraphQL: introspection disabled, schema recovered (partial, may lack types and fields)` above the endpoint's operations.

**graphql** prints `{"data":{"__schema":{…}}}`, the server's answer to the standard introspection query. With several endpoints it prints one object keyed by endpoint URL, `{"https://app/graphql":{"data":{"__schema":…}},…}`; `-origin` keeps the endpoints of one origin, or the one at a URL (`-origin https://app/graphql`), to get a file a tool loads as it is. **sdl** prints each endpoint's schema under a `# URL` comment: types, interfaces, unions, enums, input objects, custom scalars and directives with descriptions, defaults and `@deprecated`, without the built-in scalars and directives; a `schema { … }` block when the root types are not simply `Query`, `Mutation` and `Subscription`. Concatenated schemas of several endpoints are not one schema: pick one with `-origin`.

**burp** writes `{"target":{"scope":{"advanced_mode":true,"include":[…],"exclude":[…]}}}`. When the run had a scope, `include` holds its allow rules (`-scope` and `-allow`) and `exclude` its deny rules (the program's out-of-scope entries and `-deny`), each for any protocol, port and path: a domain is `{"enabled":true,"protocol":"any","host":"^(.*\\.)?example\\.com$"}` (it and its subdomains), one host `^api\\.example\\.com$`, an address `^192\\.0\\.2\\.7$`, a range as Burp takes it (`10.0.0.0/24`). The scope is read back from the run's options: a scope file again (stored by its full path), and a platform's program (`-scope hackerone -program x`) as it stands now, from bounty-targets-data. A run without allow rules, or whose scope file is gone (a note on stderr says so), includes every web service it found: `{"enabled":true,"protocol":"https","host":"^app\\.example\\.com$","port":"^443$","file":"^/.*"}`. `azhaq run -scope` reads the file back.

### fuzz reports

`fuzz -o FILE -of FORMAT` writes ffuf's report files, in the order the inputs were asked, when the run ends (also when it is stopped, by `-maxtime`, the budget or Ctrl-C). A report that cannot be written is a `failed` entry in the summary (exit 3), not a silent loss; the place is tested before the first request.

| `-of` | File |
| --- | --- |
| `json` (the default for any name but the suffixes below) | `{"commandline","time","results":[…],"config":{…}}`: results as the `-json` line above, with `input` values as plain text; `config` holds ffuf's keys for the run (`url`, `method`, `headers`, `matchers` with the filters calibration added, `inputproviders`, …) |
| `ejson` | the same without `config`, `input` values in base64 |
| `csv`, `ecsv` | a header of the keywords, then `url,redirectlocation,position,status_code,content_length,content_words,content_lines,content_type,duration,resultfile,Ffufhash`; `ecsv` has the input values in base64; `duration` as Go prints it (`1.2ms`) |
| `html`, `md` | ffuf's page and table |
| `all` | one file of each of the six, named FILE.json, FILE.ejson, FILE.html, FILE.md, FILE.csv, FILE.ecsv |

A name ending `.csv`, `.ecsv`, `.html`, `.md` or `.ejson` takes that format without `-of`; a name ending `.txt` and no `-of` gets the text of stdout. `-or` writes no file for a run with no matches (the summary says so). `-od DIR` writes each match's request and answer as one file named by the md5 of its text, shown as `| RES |` in the text output and `resultfile` in the reports.

## gallery

`azhaq gallery -db FILE` serves the screenshots of a workspace (`shots`, `run -screenshots`) to a browser on this machine, at `http://127.0.0.1:7180/` (`-listen ADDR` changes it; `127.0.0.1:0` takes any free port). `-db` may be given more than once, and `-workspace DIR` takes every `*.db` file of a directory and of the directories directly in it; the pages are merged in one view, each labelled with its workspace. A database that is not a workspace is skipped with a note; one that cannot be read is skipped and the exit code is 3. The workspace is opened read-only and read once at start (start it again to see pages taken since). A page shot in more than one run is listed once, with its newest picture.

The page is embedded in the binary: no CDN, no external font, no request to anything but the gallery's own address. The server sends nothing to any target: pictures, headers, TLS, console and network log are read from the workspace and the picture files, and the page's policy (`Content-Security-Policy`) lets the browser load only its own script and style. A gallery bound to a loopback address answers only requests that name a loopback host; bound elsewhere (`-listen 0.0.0.0:7180`) it shows every page in the workspace to anyone who can reach it, and says so on stderr.

The views:

- **Pages**: a grid (or a table) of thumbnails, each with its URL, title, status and technologies, paged (48, 96 or 200 at a time) and sortable by URL, host, title, status, look-alike group or newest. The side panel filters by status, technology, host, title text, partial or complete, and workspace, with the count of each value under the other filters. *One per look-alike group* shows one page for each group, with how many pages of it match.
- **Search** (the box at the top): words and `"phrases"` match the URL, the title and the page text; `url:`, `title:`, `host:`, `body:`, `header:`, `tech:`, `status:` (`200`, `4xx`, `none`) and `p:` (the start of a perceptual hash) match one field; a term with a `-` before it leaves out the pages that match. `body:` and free words read the text of the pages whose HTML was kept (`shots -shot-html`); the page says for how many that is.
- **A page**: the full picture, response headers, cookies (from `Set-Cookie`), TLS, the network log, console messages, the page text and its HTML source (when kept), the pages that look like it, and what the workspace holds of its URL (entity, links, observations) with the `azhaq show -db … URL` command that prints it all.
- **Look-alikes**: the groups of 2 or more pages whose perceptual hashes are at most 10 bits apart (as in `export -format html`), largest first.
- **Not taken**: the pages that gave no picture, with the run's reason: errors, and notes for pages left out on purpose (`-shot-codes`, the budget).
- **Statistics**: pages, status codes, technologies, groups, headers, requests and console lines, and what could not be shown.

What the gallery cannot show it says: a banner and `/api/stats` count the pages whose picture file is gone from disk (partial: exit 3), whose workspace holds no perceptual hash or status (taken by an older azhaq), and whose text was not kept.

### The JSON API

The page uses this API, which is open to scripts on the same address. Every response is JSON except the pictures; errors are `{"error": "…"}` with status 400 (a bad parameter) or 404.

| Path | Answers |
|---|---|
| `GET /api/` | the list of these endpoints |
| `GET /api/shots` | `{total, offset, limit, shots, took_ms}`. Each shot: `id`, `workspace` (when several), `url`, `final_url`, `host`, `title`, `status` (0: none recorded), `technologies`, `partial` (with `partial_why`: `3 off-scope assets blocked: cdn.jsdelivr.net`, or how many images and styles did not load), `hash`, `group`, `group_size`, `taken_at`, `has_file`, `body_kept`; with `collapse=1` also `group_matches`. Query: `q` (the search above), `status` (repeatable, comma-separated; `200`, `4xx`, `none`), `tech` (repeatable, all must hold; a name such as `nginx` matches `Nginx:1.25.3`), `title`, `host` (contains), `workspace`, `partial` (`yes`/`no`), `group` (a group number), `sort` (`url`, `host`, `title`, `status`, `group`, `time`), `order=desc`, `collapse=1`, `offset`, `limit` (1 to 500, default 48) |
| `GET /api/shots/{id}` | one shot as above, plus `group_members` (up to 24 other pages of its group), `show_command`, `record` (the stored row: `headers`, `tls`, `network`, `console`, `response_code`, … as in the `shots` row), `body_text` and `body_html` (when kept; cut at 20 and 64 KB, `body_cut`) |
| `GET /api/shots/{id}/show` | `command`, `entity` (type, key, first and last seen), `links` and `observations` of the page's URL |
| `GET /api/facets` | counts for `status`, `technologies`, `hosts`, `partial` (and `workspaces`) under the same query parameters, each facet under the filters other than its own |
| `GET /api/groups` | `{total, groups}`, each `{group, size, sample, title, hosts}`, largest first; `min` (default 2), `limit` |
| `GET /api/failed` | `{total, offset, limit, failed}`, each `{url, kind, reason, at}`; `q`, `kind` (`error` or `note`), `offset`, `limit` |
| `GET /api/stats` | pages, workspaces (with sizes), `statuses`, `technologies`, `groups`, `largest_groups`, `partial`, `headers`, `network_requests`, `console_lines`, `not_taken`, `files_missing`, `body_text` (`kept`, `indexed`, `ready`) and `warnings` (`message`, `partial`) |
| `GET /img/{id}/thumb` | the picture as a 360 pixel wide JPEG |
| `GET /img/{id}/full` | the picture file as taken (only a PNG or JPEG is ever served) |

A page's `id` is stable for a workspace file and URL. The first page of 2,000 pictures answers in about a millisecond and a filter in a few; thumbnails are made when first asked and kept in memory.

Exit codes: 0 when stopped with Ctrl-C and everything could be read; 1 when no workspace could be read or it holds no screenshot; 3 when a workspace was skipped or picture files are missing, said on stderr and on the page.

## crawl

`crawl` prints one URL per line, as katana does: every page it asked and every URL it found. Lines of katana's default list are left out as there: images, fonts, archives, media, `.pdf`, `.txt`, `.map` (`-ndef` keeps them, `-ef php,bak` adds to the list, `-em php,html` lists only those, `none` for URLs without one, and `-mr` and `-fr` match the printed URL by regex). `-em` and `-ndef` also show scripts and styles; `-assets` does too. These filters limit what is printed, not what is crawled. `-json` is the map's rows and is not cut by the extension list.

| Flag | Output |
| --- | --- |
| `-jsonl` (`-j`) | katana's line: `{"timestamp", "request": {"method", "endpoint", "tag", "attribute", "source"}, "response": {"status_code", "technologies", "forms": [{"method", "action", "enctype", "parameters"}], "content_length"}, "error"}`. `tag` and `attribute` say where the URL was read (`img` `srcset`, `header` `link`, `form` `action`, `call`, `js`); `source` is the page. A URL found and not asked has no `response`; a route with other methods has a line for each. `azhaq ingest` reads these lines back. |
| `-f url,path,…` | the fields katana prints, from the URL: `url path fqdn rdn rurl qurl qpath file ufile key value kv dir udir`. `-ot '{{rdn}}{{path}}'` fills a template with them, `-sf key,dir -sfd DIR` writes them to `DIR/SCHEME_HOST_FIELD.txt`, `-lof` lists the field names, `-eof request.tag,tech` leaves fields out of `-json` and `-jsonl`. |
| `-rejected` | the strings read from scripts and pages and kept out of the URLs: text, `string<TAB>reason`; `-json`, `{"rejected", "reason", "url", "source", "via"}`. `url` is what the string makes against the page. They are never asked. |
| `-do` | the URLs found outside the crawl's scope, never asked: text, the URL; `-json`, `{"url", "coverage":"out-of-scope", "source", "tag", "attribute"}`. |
| `-sr` | each answer written to `-srd DIR` (`katana_response`) as `HOST/SHA1.txt` (the URL, the request line, the status line, the headers, the body; `-ob` leaves the body out), with an `index.txt`. |

The summary counts the rejected strings and the links outside the scope, names a host that answered 429 or 503 and what was done about it, says how many POST forms `-submit-forms` sent, and says which POST forms it left alone and why. A crawl never drops links without a word: when `-max-items`, `-max-requests`, `-mdp` or the run's `-timeout` stops it, the run exits 4 and `azhaq resume` continues it.
