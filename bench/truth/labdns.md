# The local DNS lab (bench/labdns)

`go run ./bench/labdns -addr 127.0.0.1:5354` answers the zone azqlab.lan and forwards every other name to 1.1.1.1. It follows CNAMEs the way a recursive resolver does: when a CNAME points outside the zone and the target does not exist, the answer is NXDOMAIN and carries the CNAME chain.

| Name | Answer | What a correct tool reports |
| --- | --- | --- |
| azqlab.lan, www, app, mail, dev, vpn | A 127.0.0.1 | live |
| api, staging | CNAME app.azqlab.lan → 127.0.0.1 | live, with the CNAME |
| real.wild.azqlab.lan | A 127.0.0.3 | live: a real name inside a wildcard zone |
| anything else under wild.azqlab.lan | A 127.0.0.2 (wildcard) | not live: the wildcard's answer |
| old-shop | CNAME azq-lab-gone-7c1e.azurewebsites.net (NXDOMAIN) | a dangling CNAME: takeover candidate (Azure) |
| assets | CNAME azq-lab-gone-7c1e.azureedge.net (NXDOMAIN) | a dangling CNAME: takeover candidate (Azure CDN) |
| docs | CNAME azq-lab-gone-7c1e.us-east-1.elasticbeanstalk.com (NXDOMAIN) | a dangling CNAME: takeover candidate (AWS Elastic Beanstalk) |

All three dangling targets answer NXDOMAIN, so checking them needs DNS only, never an HTTP request to a cloud provider.
| any other name under azqlab.lan | NXDOMAIN | not live |

azqlab.lan is not a special-use name, so tools resolve it through the resolver they are given rather than the system's. Do not edit this file to make a tool pass.
